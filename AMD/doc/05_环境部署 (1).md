# 05 · 从本机开发到 ROCm 离线容器

## 1. 先确认环境，而不是先下载最大的模型

记录 GPU 型号/gfx 架构、显存、宿主驱动、ROCm、OS、Python、推理后端、Vivado/Vitis 的版本与官方镜像 digest。ROCm、PyTorch、推理 kernel 与量化格式不是任意拼接可用；按官方兼容路径准备，不在已有 CUDA 环境中混装一套不明来源的 ROCm wheel。[R06][R14]

```bash
python3 scripts/doctor.py > environment.json
```

这条只检查工具是否存在和基本信息，不等于模型或许可证已经验证。Windows 可以做 Python 单元测试与部分开发；最后必须在官方要求环境重跑。

## 2. 路径 A：7B FP16 + vLLM ROCm

开发期按 vLLM/AMD 对具体 GPU 和 ROCm 的官方说明安装匹配版本。不要直接使用面向 CUDA 的通用安装步骤推断 ROCm 已可用。保存 wheel 文件、依赖列表、镜像、版本与校验和；正式运行时不安装、不下载。[R06]

从官方模型仓库预先获取完整的 Qwen2.5-Coder-7B-Instruct，包括权重、config、tokenizer、chat template 和许可证。[R08]

```bash
export MODEL_DIR=/models/Qwen2.5-Coder-7B-Instruct
export HIP_VISIBLE_DEVICES=0
bash serve/start_vllm.sh configs/local.json
```

脚本的起始设置是 FP16、单卡、单并发、8192 上下文、显存占用目标 0.85，且关闭 CPU offload。这些是实验起点，不是兼容或容量承诺。检查启动日志确实选中了目标 GPU；记录模型加载后与长请求时的显存峰值。

## 3. 路径 B：量化候选 + llama.cpp HIP

可从官方 Qwen GGUF 仓库或依据合法原始权重转换，保存量化方式、转换脚本、版本与产物哈希。不要把任意第三方 GGUF 的文件名当作来源证明。[R08]

开发期按实际 gfx 架构构建固定 commit 的 llama.cpp。下面 `ACTUAL_GFX_TARGET` 是必须由真实环境填入的值，不是可以原样执行的架构名称：[R07]

```bash
# 已在开发期取得并固定 llama.cpp 源码；不要在正式沙箱 git clone。
export ACTUAL_GFX_TARGET=gfxXXXX
HIPCXX="$(hipconfig -l)/clang" HIP_PATH="$(hipconfig -R)" \
  cmake -S . -B build -DGGML_HIP=ON \
  -DGPU_TARGETS="$ACTUAL_GFX_TARGET" -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j 8
```

启动：

```bash
export LLAMA_SERVER_BIN=/opt/llama.cpp/build/bin/llama-server
export MODEL_GGUF=/models/model-q4_k_m.gguf
bash serve/start_llamacpp.sh configs/local.json
```

脚本请求全部层卸载到 GPU、单并发并关闭上下文自动滑动。**必须检查日志中实际 offload 的层数、设备与峰值显存**；请求全部卸载不等于证明真的完整驻留。不要靠 CPU 分层、统一内存或跨卡让超限模型“勉强能跑”。

若量化 kernel 不兼容，先回退到已验证的 7B FP16 路径，不要通过随意伪装 gfx 架构掩盖问题。数据中心卡上支持的 AWQ 路径不能自动推广到全部消费级卡。[R14]

## 4. 服务和客户端配置保持一致

`configs/local.json` 的 `model` 为服务别名 `local-rtl`，`base_url` 为 `http://127.0.0.1:8000/v1`。启动脚本从同一个 JSON 读取上下文和别名。模型的真实路径由环境变量指定，并应在 `MODEL.md` 声明。

每次更改上下文、量化或生成上限，必须重新检查峰值显存，并在同一配置下重跑基线。不要一边用短上下文跑基线，一边给 agent 开长上下文。

## 5. EDA 命令验证

先按实际安装位置加载 Vivado 2025.2 的 `settings64.sh`，再检查 `xvlog`、`xelab`、`xsim`、`vivado`。用包内已知正确的人工计数器进行真实工具验收，先把模型排除出诊断链。

```bash
python3 scripts/evaluate_submission.py examples/counter/task.json \
  examples/counter/reference_for_humans.sv /tmp/manual-counter-check
```

成功后检查网表、测试台标记、5 ns 时钟绑定和时序/利用率报告。此时仍是一个学习示例的局部通过，不代表所有公开题或官方题都能跑。

## 6. Dockerfile 的真实状态

包内 `Dockerfile` 是**对接模板**，没有猜测官方镜像名字。构建时 `BASE_IMAGE` 必须指定官方基础镜像，或能够证明继承自官方基础镜像、已离线安装匹配推理依赖的镜像。

```bash
docker build --build-arg BASE_IMAGE="$OFFICIAL_PREPARED_IMAGE" -t rtl-agent:locked .
```

这个模板只复制自研程序，并不会自动替你安装数十 GB 的 EDA/模型/推理依赖。最终权重是 COPY 到镜像还是按官方约定只读挂载，须等待提交规则。无论采用哪种方式，赛事运行时不能依赖外网拉取。

参考启动方式（设备、用户、组、许可证和路径以官方沙箱为准）：

```bash
docker run --rm --network none \
  --device=/dev/kfd --device=/dev/dri \
  -v "$MODEL_HOST:/models:ro" \
  -v "$TASK_HOST:/tasks:ro" -v "$RUNS_HOST:/runs" \
  -e MODEL_DIR=/models/Qwen2.5-Coder-7B-Instruct \
  -e INFERENCE_ENGINE=vllm \
  rtl-agent:locked /tasks/task.json /runs/job001
```

这是开发参考，不是已验证的官方命令。不要为了图省事添加 `--privileged` 或把宿主整个文件系统挂进容器。限制 CPU/内存/进程数/磁盘写入量，给 EDA 与模型服务需要的 cache/HOME/tmp 提供明确可写位置。严格只读运行要逐个确认工具的写目录，不能简单加 `--read-only` 后假定 EDA 不受影响。

## 7. 容器启动与计时

`serve/container_entrypoint.sh` 启动一个本地服务，确认模型别名可用后调用 `run.sh`，退出时清理服务进程组。它输出服务日志和 `container_timings.json`，记录加载耗时与端到端耗时；`summary.json` 记录预检查/基线/agent 的共同运行时间。

需要分别报告冷启动、热启动、模型生成、编译、仿真、综合、排队和总耗时。官方成本口径还未明确，保留原始数据后再按官方公式计算，不提前把某部分成本藏掉。

## 8. 断网前的准备

完整预置模型和 tokenizer；保存所有推理依赖；固定模型 commit/sha256、后端版本、编译目标和镜像 digest；验证 EDA 许可证能在官方断网方式下使用；把技能、配置和源码设置为不可变资产；从空缓存且网络关闭的环境完整跑一遍。

没有显卡时也可先完成 Python、状态机、任务适配、测试台、日志和 EDA 命令调试。不要为了开始写代码就急着购买新的 32 GB 显卡；先利用赛事验证平台确认目标型号与可用工具栈。
