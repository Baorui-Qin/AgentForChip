# 09 · 如何更有效地使用 AI 完成项目

## 1. 每次提供一个可复現的故障包

最有帮助的输入不是一张只截到最后两行的报错图，而是完整原题、输入 manifest、候选源代码、第一条错误及附近日志、工具版本、确切命令和运行目录。功能错误再增加首个失败前后的输入/状态/期望输出；涉及保密评测题时，遵守赛事的数据分享与工具使用规则。

模型服务问题要补充 GPU/gfx、ROCm、推理后端版本、模型/量化、上下文、输出上限、并发、峰值显存、原始 HTTP 响应。不要共享密钥、访问 token 或私有许可证内容。

## 2. 分工清楚的一次迭代

你先确定这轮只改哪一项；AI 提出假设和最小补丁；你运行真实工具；再把原始结果反馈给 AI；最后在冻结回归集验证，并保留或回退。一次不要同时换模型、量化、prompt、技能和重试预算，否则即使提升也不知道原因。

## 3. 可直接复制：实现一个模块

```text
项目是单卡 32 GB、断网容器内的 RTL 代码生成智能体，最终 EDA 只能使用 Vivado/Vitis 2025.2。
这轮只修改【模块路径】来实现【明确目标】。

请先阅读现有接口与测试，不要改动 baseline 的“原题、一次生成、无工具、无技能、无重试”行为。
不能修改可信测试台、题目、模型权重、其他无关模块，不能加入运行时联网依赖。
请交付：问题复现说明、最小代码修改、新增测试、运行命令、预期日志和未验证项。
任何缺少真实 Vivado/GPU 环境的测试都明确标注为未做，不虚构通过率。
```

## 4. 可直接复制：定位功能错误

```text
请分析下面 RTL 的首个功能不匹配，而不是重新猜题意。
【完整题目与接口】
【当前候选源代码】
【测试台来源和可见性：公开/人工编写/允许调用的反馈】
【Vivado 版本与命令】
【首个失败周期、输入、前态、期望、实际】
【相关日志】

先列出最可能的 1—3 个根因，并说明什么测试能区分这些假设。
给出保持接口、复位、signedness 和延迟不变的最小修复。
不得改 scoreboard、成功标记或约束来绕过测试；测试台本身可疑时请明确提出独立核查办法。
最后补充至少两个能防止此类回归的边界用例。
```

## 5. 可直接复制：审查部署

```text
请审查这套离线部署配置。目标 GPU 是【型号/gfx】，ROCm【版本】，
官方基础镜像【digest】，推理后端【版本】，模型【仓库/commit/量化】，
上下文【值】，输出上限【值】，并发【值】。
附件为 Dockerfile、启动脚本、MODEL.md、环境日志和显存记录。

只根据明确证据判断是否能在单张 32 GB 卡完整容纳；不要只看权重体积。
检查 CUDA/ROCm 依赖混用、隐含联网、CPU offload、跨卡、可写目录、权限和许可证风险。
区分已经实测和仍需验证的事项，并给出最小验证命令。
```

## 6. 可直接复制：审查实验结论

```text
比较 A 与 B 两个版本，固定模型、任务、种子方案、工具版本和共同预算。
这里是逐题逐次结果、耗时和配置哈希；simulated=true 的记录不计入真实实验。

请区分绝对百分点增益和相对增益，检查 pass@5 是否来自至少 5 次独立完整运行，
不要把内部修复计为独立样本。按错误类别分析回归，指出可能的数据泄漏与选择性报告。
官方评分公式尚未公布，不要给出假官方分数。
最后建议下一轮只修改一个最有证据支持的因素。
```

## 7. AI 不能替你省掉的事情

运行真实 ROCm/Vivado/Vitis、核查测试台正确性、验证模型来源与许可、确认官方接口/预算、维护留出集和做最终断网复现，都需要实际环境与可靠记录。AI 可以写脚本和解释证据，不能仅靠“看起来合理”把未测项目标为已完成。
