# 02 · 总体架构与算法原理

## 1. 架构：把自由度放在代码生成，把判定权交给固定工具

```text
原始题目 + 明确接口 + 可见测试资产
                 │
                 ▼
       只读任务适配层 / 规范契约
                 │
                 ▼
          BM25 检索少量技能
                 │
                 ▼
       本地单模型生成完整候选
                 │
                 ▼
  代码提取 / 自包含与测试隔离检查
                 │
                 ▼
          xvlog → xelab
                 │
                 ▼
  xsim + 可信测试台（没有则 UNKNOWN）
                 │
                 ▼
       synth_design + 输出网表
                 │
          成功 / 首个失败原因
                 │
                 ▼
      预算内修复，保留最好候选
                 │
                 ▼
   最终代码 + 逐次证据 + 基线 + 日志
```

模型不直接执行 shell、Tcl、任意 Python 或修改测试台。工具调用由固定 Python 代码决定；Tcl 文件也是固定脚本。这样可降低工具误用和不可复現的自由规划行为。

## 2. 有限状态机

定义状态为 `GENERATE → CHECK_SOURCE → ANALYZE → ELABORATE → SIMULATE → SYNTHESIZE → ACCEPT/REPAIR/STOP`。只有上一步证据有效才推进。没有测试台时，允许继续综合获取结构证据，但不能越过功能判定层，也不能宣称全通过。[R03][R04]

原型使用循环而不是额外的工作流框架，便于审查、离线部署和调试。新功能应当首先体现为状态和判定条件的变化，而不是把复杂度全部塞入提示词。

## 3. 反馈引导的程序修复

设原题为 s，候选为 c_t，工具反馈为 f_t，技能为 K(s,f_t)。下一轮生成可写为：

```text
c_(t+1) = Model(s, best_candidate, compact_feedback, retrieved_skills)
```

这与“反例引导程序合成”的思路相近：不符合约束的候选被反例排除，搜索集中到尚未满足的要求。但本方案的反例来自有限测试，不是完备形式验证，**不能称为严格的 CEGIS 正确性证明**。VerilogCoder 展示了规划和工具反馈在 Verilog 智能体中的研究方向；本包不是该论文系统的复刻，也没有实现其中完整的 AST/波形工具。[R10]

例如原题要求加一计数器，第一次候选却每次加二：

```text
first_mismatch cycle=2, rst=0, en=1
expected q=1
actual   q=2
```

下一轮应修复增量或相关位宽，而不是改变测试台、接受条件或题目。开发者还应核查测试台是否正确，因为错误测试也能把模型引向错误实现。

## 4. 先修什么：错误分类

| 类别 | 例子 | 动作 |
|---|---|---|
| 环境错误 | 缺工具、许可证失败、动态库缺失 | 停止生成，修环境；不要反复让模型重写 RTL |
| 输出格式错误 | 代码截断、多个竞争代码块、模块名错误 | 要求完整且唯一的候选 |
| 编译/展开错误 | 语法、端口、未定义模块 | 优先修第一个根因，避免追逐级联报错 |
| 功能错误 | reset、优先级、位宽、延迟、边界条件 | 提供首个反例和必要前态，最小修改 |
| 综合错误 | 多驱动、不支持的构造、资源实现问题 | 结合综合日志修改，仍须保持行为 |
| 无可用功能证据 | 只有题目，没有测试台/API | 只报告结构检查；开发下一步是独立测试设计 |

原型先用确定性日志规则分类，分类不清时保留原始错误，不装作已经精确定位。未来可增加“由模型提出根因假设”，但假设仍需工具验证。

## 5. 为什么保留最好候选

为有可信测试的候选定义工程等级：0 未编译通过，1 编译通过，2 仿真通过，3 仿真与综合均通过。候选更换按该等级优先，不因新生成代码更长或自称更正确而替换旧候选。无测试台时最高只能获得功能链条中的第 1 级；综合成功只作额外结构证据。

修复失败会回到已取得最好证据的候选。候选哈希完全重复时停止，避免无意义循环。原型不是 beam search，只保存最好候选；若以后扩展 beam，可保留 2 个有实质差异的实现，但先测成本是否值得。

## 6. 技能检索：小规模 BM25 足够起步

把技能拆成 reset、位宽、移位、组合完整性、时序、FSM、FIFO、参数、存储、诊断、时序约束、综合等 12 张卡。每张卡应包含触发条件、常见失败原因、修复原则和验证边界，而不是整题答案。

使用词频和逆文档频率搜索相关卡片。原型采用平滑 IDF 的 BM25 变体：

```text
score(q,d) = Σ IDF(t) · f(t,d)(k1+1) /
             [f(t,d)+k1·(1-b+b·|d|/avgdl)]
IDF(t) = ln[1 + (N-df(t)+0.5)/(df(t)+0.5)]
k1 = 1.5, b = 0.75
```

英文按词切分，中文使用字符二元组。选择最相关的 3 张，额外上下文不足时从末尾去掉卡片。BM25 的词频饱和、文档长度归一化和 IDF 思路见 Stanford 信息检索教材；本包使用的平滑 IDF 写法是工程实现选择。[R13]

当技能只有几十张时，没有必要额外加载一个 embedding 模型占显存。BM25 不理解全部语义，别把检索得分当作正确性证据。是否带来提升要由消融实验回答。

## 7. 上下文管理

每次请求只保留原题、当前最好候选、少量技能、必要错误摘要。不得把几十轮全部历史与完整几万行日志塞回模型。

本包的核心代码不依赖 tokenizer，采用保守的 UTF-8 字节预算近似，并预留模板开销；它可能过度拒绝长题，**不是精确 token 计数器**。不截断原题和候选，只缩短可选技能与错误摘要。真实 token 限制以所选服务/分词器为准；后续可接入已固定版本的 tokenizer 做精确计数。

较长的任务首先提高已实测可容纳的上下文上限，或者优化日志摘要，而不是悄悄删掉题目后半段。baseline 与 agent 必须使用同一个服务上下文配置。

## 8. 预算算法

用单调时钟维护共同截止时间；每个外部工具获得 `min(阶段上限, 剩余时间)`。达到超时后终止该进程组，保留日志。首次稳定通过即停止，不为“多想一想”继续生成。

开发用默认值为上下文 8192、输出上限 2048、最多 4 次模型调用、共同运行预算 600 秒。它们不是赛事规定，也不是经真实 GPU/EDA 调优后的最优数值。基线、预检查、智能体在成对入口中共用总预算；服务冷启动由容器入口另行记录。官方预算公布后必须同步调整。

进一步优化可以估计某类重试的单位时间收益：`预期新增通过概率 / 预期耗时`。先在开发集积累统计，再决定何时局部修复、何时重写、何时停止；不要提前写一个未经校准的复杂强化学习控制器。

## 9. 模型选择与显存原理

以可复現部署为先，不把下面的候选表理解为 2026 年“最新最强排名”。模型越新或通用代码榜单越高，不代表本赛道综合通过率越高。

| 阶段 | 建议比较的候选 | 目的 |
|---|---|---|
| 第一版 | Qwen2.5-Coder-7B-Instruct，FP16 | 先验证稳定的本地生成与完整 EDA 闭环 |
| 第二版 | Qwen2.5-Coder-14B-Instruct，兼容的 4-bit 路径 | 在同预算下验证更强能力能否抵消耗时 |
| 对照 | Qwen3-8B 等可合法部署的开源候选 | 实测硬件任务，不凭通用榜单直接判断 |
| 后续 | 32B 量化或硬件专用模型 | 只有部署、成本和可重复收益均成立才采用 |

官方模型仓库提供模型与推理信息；硬件专用方向可参考 RTL-Coder，但仍需审计模型来源、许可、适配与数据交叉污染。[R08][R09][R11]

显存粗估不能只看权重文件：

```text
M_total ≈ M_weights + M_KV + M_activations/workspace + M_runtime
M_weights ≈ 参数量 × 每参数位数 / 8
M_KV ≈ 2 × 层数 × KV头数 × head_dim × 序列长度 × 每元素字节 × 并发序列数
```

其中 2 表示 K 和 V。量化元数据、某些未量化层、缓存和图执行会产生额外占用，MoE 的激活参数量也不等于全部驻留权重。以 7B/14B/32B 的名义参数量估算，16-bit/4-bit 权重的理论体积只是约 14/7/16 GB（十进制）这些数量级，不能当实测峰值。

ROCm 量化支持与具体 GPU、推理版本和量化格式相关。AMD 的某些 AWQ 说明限定特定 Instinct 系列，不能据此保证赛事的 32 GB 消费/工作站卡支持完全相同的路径。可把 vLLM FP16 作为首个部署候选，把 llama.cpp HIP + GGUF 作为量化备选；最终都要验证整模型驻留在单卡，不用 CPU offload 掩盖超限。[R06][R07][R14]

## 10. 应当延后、但值得研究的算法

稳定闭环之后，再考虑规范契约自动抽取、独立测试生成、首个失败波形切片、AST 依赖回溯、有限分支搜索、诊断驱动技能选择，以及开发期训练。每加一项都保留原有简化版本做消融。对保密评测期间的题目不持续修改技能库，不把前一道评测题答案累积成下一题的检索资产。

## 11. 官方不提供测试台时，闭环怎样继续

应根据实际权限选择三条不同路径，而不是假定能读到保密参考实现：

| 可用信息 | 允许采取的方法 | 结论边界 |
|---|---|---|
| 有公开可信测试台 | 固定测试台直接 xsim，返回首个反例 | 通过该测试，不等于通过全部隐藏测试 |
| 有可调用的官方反馈接口 | 按调用预算和权限获取失败摘要 | 只使用接口允许返回的信息 |
| 只有题目和接口 | 建立独立契约、边界测试、不变量或变形测试，再做结构检查 | 自建测试属于辅助证据，不能冒充官方判定 |

第三种情况下，下一步实现可以由一个独立测试生成阶段读取原题，先输出“输入域、状态转移、输出时刻、边界条件”的结构化契约，再生成测试台。该阶段不读取当前候选代码，以降低二者共享同一错误的概率。对于计数器可验证保持、加一、回绕、复位优先级；对于组合运算可验证穷举小位宽与数学不变量；对于 FIFO 可验证顺序、计数界限与允许的同时操作。

测试台仍必须经过人工或独立方法审核，并用故意错误的 DUT 做 mutation testing。将自建测试与官方反馈在日志中使用不同来源标签，冻结后不能由候选生成器修改。相同模型生成测试与实现仍可能出现相关错误，分角色不等于真正独立证明。

**本包没有自动完成这套通用测试生成阶段。** 目前缺少测试台时会明确输出功能未知；这是需要依据官方反馈条件优先补齐的扩展，而不是在统计里补上一个默认 PASS。
