# RTL 参赛方案对齐实施计划

编写日期：2026-09-28。阶段 0、1 已按显式 mock 范围完成，详见[执行记录](RTL_Alignment_Stage01_Execution.zh.md)。阶段 2 已完成解题器分离实现，阶段 3 已按用户后续授权完成 DeepSeek API 替代小样本；完整验收仍缺 OS 读取隔离及本地 Qwen/GPU 实测，详见[阶段 2、3 执行记录](RTL_Alignment_Stage23_Execution.zh.md)。未产生比赛成绩；阶段 4-7 尚未实施。

## 1. 总结与目标

当前项目已经有较完整的 RTL 生成、修复、Vivado 验证、网表验收和证据记录能力。下一步不是重写智能体，而是把已有能力整理成与参考仓库兼容、能在目标环境中独立运行的参赛方案。

最重要的差距有四项：

1. 现有入口以本地实验 UUID、固定题库和 campaign 为中心，不是参考方案的单题目录输入、标准文件输出。
2. 现有 P10 修复能够使用参考评测器反馈；正式解题服务不能依赖不会下发的测试台、参考实现或按题号绑定的 oracle。
3. 最近的正式实验使用 DeepSeek API；本地千问的真实工具调用、批测接入、单卡显存与断网部署尚未形成同等证据。
4. 现有实验的基线、采样、环境和验收协议不同于参考方案，不能直接把现有通过率或增益作为比赛成绩。

最终目标：从收到一道未预先登记的题目开始，在预算内调用本地模型和允许的工具，产出候选 RTL 与完整 trace；由独立测试器按照参考规则评定 L0-L3，并与参考仓库原版基线比较。

执行顺序：**先固定规则和输入输出，再消除参考答案依赖、接入本地模型，随后完成目标环境与服务打包，最后做一致口径的测试和优化。**

## 3. 按参考方案安排交付物

以下是未来方案包的目标结构，不是当前已经存在的完整提交包。实际队名与输出目录在阶段 0 确定。

```text
<team_name>-agent/
  Dockerfile
  manifest.json
  baseline.py
  run_baseline.sh
  run.sh
  model/
    MODEL.md
  agent/
  skill/
    README.md
  serve/
  REPORT.md
```

| 参考位置 | 应放内容 | 处理原则 | 主要阶段 |
|---|---|---|---|
| `agent/` | 现有框架所需的运行产物、配置及单题调用逻辑 | 不复制整个研究工作区，不重写核心 agent loop | 1-3 |
| `run.sh` | `run.sh <task_dir> <out_dir>` 适配入口 | 不能仅给现有脚本改名；现有参数语义不同 | 1 |
| `baseline.py`、`run_baseline.sh` | ZIP 提供的原版基线 | 保留字节和 SHA，不替换成现有 P10 基线 | 1、3 |
| `skill/` | 通用 RTL 规则、提示词及确定性检查 | 不含按题号查答案、参考源码或隐藏测试资产 | 2、7 |
| `model/MODEL.md` | 权重、模板、量化、推理栈、资源实测 | 从现有模板补齐真实记录 | 3-4 |
| `serve/` | 模型服务启动配置、投题 HTTP 服务 | 优先适配参考实现，不新增无关服务框架 | 3、5 |
| `Dockerfile`、`manifest.json` | 可复现的离线运行包及声明 | 固定必要依赖，清除开发机绝对路径 | 4-5 |
| `REPORT.md` | 设计说明、实验、失败分析与限制 | 区分历史研究实验和参考口径实验 | 6-7 |
| 包外 `selftest/` | 参考判定器、题库导入及计分脚本 | 作为独立裁判，不放入智能体可读运行区 | 0、4、6 |

## 4. 分阶段任务

优先级说明：P0 是阻止有效参赛或可信测试的问题；P1 是交付和稳定性要求；P2 是在链路成立后提高得分。一个阶段完成验收后再进入依赖它的阶段，不以“已经写了代码”代替“已经验证”。

### 阶段 0：固定参考版本和验收口径 [P0]

目标：后续所有实现围绕同一份可追溯契约，不反复按照不同文档修改。

- [x] 将 ZIP 解压到独立参考目录，保留原包和 SHA；不要覆盖主工程或历史实验。
- [x] 核对 README、SCORING、API_CONTRACT 与实际脚本，形成一份规则对照表和待确认事项清单。
- [x] 固定原版基线、判定器、导入器、计分器的文件哈希。
- [x] 确定方案包位置、源码归属、使用的模型候选与目标验证机器；目标沿用既有记录的 Linux W7900，正式队名、实际云主机标识及可用性仍明确待确认，不预先假定云端服务已经启动。
- [x] 明确两套记录：现有 P10 是研究验证协议，参考 selftest 是比赛对齐协议；二者不混用成绩名称。
- [x] 把已知题面/参考冲突、初态问题和环境故障列为单独跟踪项，不私自修改参考裁判来提高成绩。

注意：参考文档概括基线为“只含题面”，但原版 `baseline.py` 还有固定系统提示词，并固定 `temperature=0`、`top_p=1`、`max_tokens=8192`。应以未经修改的参考脚本执行结果作为对齐基线，不自行重写所谓等价提示词。示例 `deadline_s=360`、selftest 的默认 timeout 和评分示例里的增益倍数，也不能当作已经公布的正式预算。

验收：能逐项指出输入、输出、失败表示、基线、环境、采样和计分所依据的文件；未知参数明确标注。该阶段不调用模型。

### 阶段 1：跑通标准单题输入输出 [P0]

依赖：阶段 0。

目标：先解决“测试器能否调用”，不把接口适配和解题质量混在一起。

- [x] 新增最小单题适配入口，通过现有受支持的 dsh profile 启动，不改坏原有 P10 命令。
- [x] 从 `<task_dir>/prompt.txt` 读题，从题面取得模块名和端口；不要求 `interface.txt`、已登记题号、UUID 或预先建立的 campaign。
- [x] 在 `<out_dir>` 写出 `solution.v` 和 `trace.jsonl`；明确空答案、内部异常和超时的不同记录。
- [x] 保持参考基线文件原样，并固定同一服务、独立调用的接入要求；本阶段不运行基线，真实同服务验证留在阶段 3，不复用 P10 初始候选。
- [x] 为每次调用建立独立工作目录；不读取上一次答案，不因题号重复覆盖历史结果。
- [x] 用显式 mock 完成文件契约测试，随后由阶段 3 接入真实模型。mock 产物只验证协议，不计入能力或增益。

验收：3 道参考示例能走完“输入目录 -> 输出文件”；空 `interface`、包含空格的合法路径、重复题号、空答案和错误参数有定向测试；原有 P10 入口相关回归仍通过。真实脚本在 Linux 的执行权限、换行及信号行为于阶段 4 再验收。

### 阶段 2：分离解题器与参考裁判 [P0]

依赖：阶段 1。此阶段必须在正式能力比较之前完成。

目标：智能体只靠正式投题时能够取得的信息解题，不能靠已知答案和隐藏测试反馈维持历史通过率。

- [x] 将参赛解题路径与研究用 P10 对照路径分开；保留现有研究路径，不全盘重构。
- [ ] 解题路径仅读取题面、自己的候选 RTL、通用技能及允许的工具输出；不能读取参考 RTL、裁判测试台、固定题号 oracle 或历史答案目录。
- [x] 首先保留接口检查、语法检查和 DUT 独立综合；需要功能自检时，再让模型依据公开题面生成自己的测试或断言。本轮不运行功能仿真。
- [x] 自建测试通过只能标记为“自检通过”，不得冒称隐藏裁判 L2 通过或独立正确性证明。
- [x] 对未知题号和新题面建立验证用例，保证不依赖 VerilogEval 清单或固定题面哈希才能开始解题。
- [x] 将裁判运行放在候选冻结之后；其结果用于最终评分，不在同一次参赛解题调用中反馈给模型继续修复。参赛路径无裁判工具，本轮未运行外部裁判。
- [x] 保留现有 P10 的严格 `final.sv`/网表验收条件。参赛入口输出的是供外部裁判判断的候选，不是通过删除原有安全门槛把候选伪装为 VERIFIED。

验收：在解题进程无法读取裁判资产的独立运行目录或隔离环境内完成未知题号测试；检查文件访问和模型请求，确认没有参考资产内容；原有严格验收的负例回归仍通过。

当前状态：代码与请求能力隔离已验证，175 项原有聚焦回归通过；Windows ACL 不限制读取，WSL 缺运行与隔离工具，故 OS 读取隔离尚未验收，不能将本阶段整体标为完成。

范围限制：不把现有 156 题网表 oracle 带入参赛技能包；不以重做全题库形式验证作为接入参赛链路的前置条件。

### 阶段 3：接入本地模型并验证原版基线 [P0]

依赖：阶段 1-2；真实验证需要可用的目标 GPU 和明确的运行预算。

目标：生成、工具调用和基线都真正来自同一份本地开源权重。

- [x] 先核对现有千问方案：`Qwen3-Coder-30B-A3B-Instruct` 的 GGUF Q4_K_M 候选及 llama.cpp 路线；当前配置不是实测完成凭据，不自动换模型或重新下载权重。
- [x] 参赛 RTL 模型入口使用可配置 provider/model，沿用现有 LLM 服务扩展点，不固定 `deepseek-official`。研究 P10 专用线路保留，未将其 DeepSeek 计数协议套到 Qwen。
- [ ] 校准所选模型的 chat template、token 计数、上下文上限和工具调用格式，不沿用 DeepSeek 专用计数器或直接套用 `reasoningEffort`。
- [x] 验证普通文本、流式工具调用、完整 JSON 参数、截断、取消、错误响应和上下文超限；截断工具参数不得执行。异常协议覆盖来自无费用 HTTP/Agent 测试，正常闭环另有真实 API 证据。
- [x] 使用原版 `baseline.py` 做真实 API 替代调用，验证 `/v1/models` 与 `/v1/chat/completions` 兼容，并记录原脚本 SHA；本地 Qwen 同服务验收仍待部署。
- [ ] 固定权重和 tokenizer/template 哈希、量化、后端版本、GPU/ROCm、上下文及采样配置；测量加载后和运行峰值显存。
- [x] 更新 `model/MODEL.md`，清除与实际候选冲突的旧占位建议；权重文件大小不作为峰值显存。

验收：同一模型服务下，至少完成一题真实 Agent 工具闭环和一题原版基线；基线仅一次生成、无 Agent/技能/工具注入；随后对 3 道示例记录实测结果。单卡完整运行不超过规则中的 32 GB，且不以验证卡具有更多显存为理由超限。

用户授权的临时替代范围已完成：DeepSeek API 下 3 道示例的 Agent/原版基线均跑通，共 9 次成功请求及 1 次网络失败发送尝试，保留全部失败证据。该结果不证明本地 Qwen、模板校准或 32 GB 单卡要求，因此原定阶段 3 的完整验收仍未关闭。

停止条件：模型不能完整加载、工具调用协议不稳定或显存超限时先修复小样本，不启动 156 题。

### 阶段 4：对齐 Linux、Vivado 和离线运行 [P0]

依赖：阶段 1-3 的实现；目标 EDA 与 GPU 环境准备可提前进行。

目标：在参考要求的环境中得到可复现结果，而不是把 Windows 开发成绩直接迁移为比赛成绩。

- [ ] 使用实际可取得的赛事镜像或明确标注的开发镜像，记录镜像 digest；参考要求为 Vivado 2026.1，最终版本仍以赛事公告为准。
- [ ] 将开发机路径改为运行配置及环境变量，如 `XILINX_VIVADO`、`EDA_TMP`；复用已有进程管理，不拼接旧版本安装目录。
- [ ] 验证编译、展开、仿真、综合、目标器件、5 ns 约束及授权；仅有版本号或编译成功不能说明整条链路就绪。
- [ ] 先使用参考 `--check` 和 `--reference` 检查 3 道示例，再运行模型方案。
- [ ] 预置权重、运行依赖、模板和通用技能；断网后不得自动安装包、下载模型或调用外部 API。
- [ ] 每次执行使用独立本地临时目录，验证超时取消及子进程清理；不能因 NFS 小文件开销掩盖超时。
- [ ] 检查 SIGTERM 后的退出和日志落盘，保留空答案与环境错误；不把授权、工具或存储失败记录成模型能力失败。

验收：参考正例通过预期 L3，故意错误候选不能被误判通过；断网条件下至少完成一轮真实 Agent 与基线运行；路径中无 Windows 开发机依赖。若缺少目标环境，本阶段标为未完成，不使用其他仿真器替代后宣称对齐。

边界：Windows 2025.2 校准库与收据不能自动授权 Linux 2026.1 的网表验收；若继续使用额外网表检查，须在新环境独立校准并单列结果，不改变参考 L0-L3 的定义。

### 阶段 5：完成 HTTP 投题与提交包 [P1，正式提交前必需]

依赖：阶段 1-4。

目标：让赛事方能可靠地投题，且干净环境能够复现运行。

- [ ] 按参考结构组装方案包，固定 `Dockerfile`、`manifest.json`、模型声明、技能说明与启动脚本。
- [ ] 实现并验证 `GET /v1/health` 和 `POST /v1/solve`，Agent/Baseline 使用同一端点的 `mode` 分支。
- [ ] 校验 Bearer token、`task_id`、`nonce`、空 `interface` 和 `deadline_s`；按参考契约返回 `solution`、`trace`、`elapsed_s`。
- [ ] 健康检查在模型或 Agent 未就绪时不得返回 `ready=true`；模型名和显存来自真实服务与测量。
- [ ] 区分“未解出，返回空字符串”和内部服务故障；约束请求总墙钟，不能仅限制单次模型调用。
- [ ] 按 ZIP 说明绑定 `127.0.0.1`，对外暴露前确认实际平台转发机制；模型推理端口不额外公开。

### 阶段 6：按照参考测试器重新建立成绩 [P1]

依赖：阶段 1-5。不得直接使用历史候选拼装新的“比赛成绩”。

目标：回答“按照参考测试运行，效果到底怎么样”，同时区分解题能力、部署故障与数据集缺陷。

- [ ] 冻结当前代码、权重、推理栈、提示词、技能、原版基线和判定器哈希，再创建独立实验目录。
- [ ] 先跑 3 道示例，每题一次；再选择预先固定的 10 题及 40 题检查兼容性、时间和费用。
- [ ] 小样本稳定后，再授权并执行全量 VerilogEval 自测；正式统计按参考要求每题独立运行 5 次，既不挑最好答案计分，也不混入人工修订。
- [ ] 每次样本包含完整的解题过程；Agent 内部重试与最终外部采样分开统计。原版 baseline 始终不额外重试生成。
- [ ] 用原版计分器报告 L0/L1/L2/L3、加权得分、pass@1、诊断性 pass@5、Agent/Baseline 增益和墙钟成本。
