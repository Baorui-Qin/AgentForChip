# 01 · 先理解赛题，再决定做什么

## 1. 本题真正要求的系统

根据你提供的四张赛题截图（第 6—9 页，收录于 `references/contest_images/`），参赛对象不是某个固定 FPGA 电路，而是一套能在断网容器中自动读题、生成硬件代码、利用工具反馈并交付代码的系统。最终交付包括模型声明、推理服务、智能体代码、技能包、基线入口和设计报告。

把它想成“会调用 FPGA 编译器和仿真器的软件工程助手”，而不是“把神经网络烧到 FPGA 上”。GPU 用来运行本地大模型；题目指定的 FPGA 器件用于 EDA 的综合目标。按截图，开发这套系统不以先购买 FPGA 板卡为前提。

## 2. 规则对应的实现决定

| 截图中的要求 | 对系统的具体影响 |
|---|---|
| 单张 32 GB GPU，不能跨卡 | 权重、KV cache、工作区总占用要实测；不要按参数量直接判断能装下 |
| 官方 ROCm 验证环境 | 先问清 GPU 架构、ROCm、Python 和基础镜像，再决定量化后端 |
| 断网沙箱 | 模型、tokenizer、chat template、依赖与技能全部预置；禁止运行时下载 |
| EDA 仅提供 Vivado/Vitis | 不能把 Icarus/Verilator/Yosys 当作正式环境默认依赖 |
| 工具链 Vivado/Vitis 2025.2 | 命令、配置、器件库和测试台兼容性在同版本验证 |
| RTL：可编译→仿真通过→可综合 | 必须分阶段存证，不得因退出码为 0 就直接判全通过 |
| `xczu3eg-sbva484-1-e`，时钟 5 ns | 固定器件；只对真实、已知的时钟端口加约束，不能虚构 clk |
| pass@1 与 pass@5 | 独立完整运行与内部修复次数分开统计，先等官方明确采样定义 |
| 同模型裸跑基线 | 保持同一模型/服务/上下文/生成设置；仅使用原题，单次生成，不重试、不调用工具 |
| 评测窗口不能修改方案、技能或权重 | 方案只读挂载；任务日志写独立目录；不做跨题在线知识更新 |

以上约束取自上传截图；具体接口、分数公式与预算仍以官方后续《评分细则》为准。本次访问官方主页/下载页未成功取得完整新版细则，不能据此推断没有更新。[R00]

## 3. 为什么主线建议选 RTL

这是一个针对当前交付范围的工程选择，不是宣称 RTL 永远比 HLS 简单。RTL 的编译、展开、仿真和综合命令路径清晰，且编译错误、端口错误、首个输出不匹配可直接作为反馈。公开 VerilogEval 提供自然语言到 RTL 的任务来源；但其原生评测依赖不能原封不动视为赛事要求。[R01][R03][R04]

HLS 适合已经很熟悉 C++、算法和 Vitis HLS 的团队。它多了精确位宽、接口协议、循环调度、存储端口与数据流死锁等问题。仅仅会写普通 C++，不代表能写好可综合 HLS。建议先完成一个 track 的可复现闭环，而不是两条主线都只有半套系统。[R02][R05]

## 4. 按评分权重安排工作

截图的评分权重为：能力 30、增益 40、墙钟效率 10、工程质量 20。**智能体和技能带来的稳定改善比“单纯找到一个更大的模型”更值得优先验证。** 但不能据此故意选择很弱的模型，或削弱基线；绝对通过率仍然重要，而且增益的归一化公式尚不明确。

建议依次投入：

1. 能完整运行并留下可信证据，解决断网/版本/接口/超时问题。
2. 用 7B 级可部署模型建立真正的裸跑基线。
3. 加入编译诊断、功能反例、综合反馈和有限次修复，测量实际增益。
4. 加入少量经过消融验证的技能，提高 pass@1 与稳定性。
5. 比较更大或更专用的候选模型；只有证据支持时才微调。

## 5. 初期不建议优先做的事

不优先训练大模型、不优先做大量相互聊天的“多智能体”、不优先做漂亮前端、不优先实现复杂向量数据库、不优先做大规模树搜索、不优先追逐未经同条件验证的榜单数字。它们都可能成为后续优化，但无法代替工具链兼容与真实测试。

## 6. 需要尽早向赛事方确认的关键问题

最紧要的是：确切 GPU 型号/架构、官方镜像与 ROCm 版本、单题/总时间和输出限制、输入输出接口、是否提供可调用的功能反馈。尤其需要区分：公开样例测试、允许调用的评估 API、仅官方可见的保密测试台。

此外确认：评分的增益公式、pass@5 的采样单位和种子规则、综合是否还要求某个时序阈值、容器离线授权方式、CPU/主存/磁盘/进程限制、基线耗时是否计入单题预算，以及 LoRA/量化权重的开源与提交形式。

这些内容不能从当前截图中全部确定。包内使用自定义任务 JSON 与开发用预算，不冒充官方接口和最终限制。
