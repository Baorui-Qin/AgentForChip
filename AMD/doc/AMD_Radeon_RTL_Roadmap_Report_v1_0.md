# RTL/HLS 本地智能体设计赛道
# 路线规划与阶段实施报告

**适用平台：AMD Radeon 显卡 + Vivado / Vitis｜规划主线：优先 RTL

## 摘要

本项目面向 RTL/HLS 本地智能体设计赛道，目标是在单张 32 GB GPU 的赛事资源约束内，使用可本地部署的开放权重模型，在基于官方基础镜像构建的断网容器中，自主完成从自然语言题目到硬件代码的生成与交付。按照已提供赛题，RTL 结果依次接受编译、功能仿真和综合判定，工具链为 AMD Vivado / Vitis 2025.2，目标器件为 `xczu3eg-sbva484-1-e`，时钟约束为 5 ns；系统还须提供同模型裸跑基线、模型声明、技能包、实测结果与复现材料。[S0]

本报告沿用此前认可的技术主线：**优先完成 RTL track，以单个本地模型为生成核心，以固定状态机组织工具调用，通过编译、合法可用的功能测试及综合反馈实施有限次修复，并用小型领域技能库提高首次成功率和修复质量。** 项目按“需求与接口确认—平台和验证链打通—基线建立—修复闭环—技能及效率优化—冻结与复现”六个阶段推进。部署侧重点是 Radeon 与 ROCm、推理后端的实际兼容性；算法侧重点是可验证的反馈利用，而非一开始追求更大模型或复杂多智能体。

规划以三个职责单元、六周参考周期组织实施，逐阶段明确负责人、交付物、退出条件和风险处置。验收以真实 EDA 证据、同条件基线对比、资源与时间记录及断网复现为依据。**本文件是一份实施规划，不是实测成绩报告；具体 Radeon 型号、团队人数、正式赛程和最终评分细则仍需落实，文中的工期、样本数和内部验收门槛均为建议值。**

## 1. 项目定位与实施边界

### 1.1 我们要完成什么

是一套自动化硬件代码生成系统，而不是某一个固定逻辑电路，也不是把大模型部署到 FPGA 上。Radeon GPU 承担本地模型推理；CPU 侧进程运行 EDA 工具。整个交付链以“读题后能够自动产出结果并解释结果依据”为终点。[S0][S3][S4]

本期保留一条主线：**RTL + 单模型 + 固定工具流程 + 有限反馈修复 + 小技能库**。Vitis 属于指定平台的一部分，但选 RTL 并不意味着每道题都要调用 Vitis HLS；只有后续决定参加 HLS track，才增加独立的 HLS 任务和判定适配器。赛事方允许两个 track 独立评比，并推荐参赛队伍只选其一（当然，我们也可以两个都做）。[S0]

### 1.2 本报告采用的规划假设

具体 GPU 型号和显存尚未提供，本文的“32 GB”指赛题约束，不代表当前显卡的实际容量。正式执行以官方镜像、设备、接口和预算为准，开发机仅作为前期实现与验证平台。[S0]

优先级为：**先合规运行和可信判定，再争取最终通过率及基线增益，最后压缩成本。** 不以故意削弱基线获取表面增益，也不把“pass@1 与 pass@5 的差值变小”单独当成功标准，因为两者都下降也可能缩小差值。

### 1.3 主路线及权限边界

主流程为：原题与接口读取 → 少量技能检索 → 本地模型生成候选 → 编译与展开 → 合法可用的功能验证 → 综合 → 根据首个根因有限修复 → 输出最佳候选及证据。控制流程固定，但不承诺模型每次输出完全相同。模型只生成候选源代码，不获得任意命令执行权；工具参数、测试资产与判定逻辑由固定程序管理。工具反馈式硬件代码生成可参考 VerilogCoder，本文不依赖其完整图规划或波形追踪实现。[S6]

## 3. 阶段组织、人员职责与关键路径

### 3.1 按职责分工，而不是按工具随意分工

| 职责单元 | 主责与交付 | 协作及复核责任 |
|---|---|---|
| A：项目统筹与智能体 | 规则台账、任务接口、状态机、修复策略、候选管理、版本集成与最终报告。 | B 审查功能判定边界；C 核对资源、推理参数和实验配置。A 决定范围取舍，不自行修改测试标准迁就模型。 |
| B：RTL 与 EDA 验证 | 人工参考样例、测试台、Vivado 脚本、日志根因分类、边界用例和失败分析。 | A 接入结构化反馈；C 复跑工具流程。B 复核“通过”是否有真实证据，并审核技能中的硬件规则。 |
| C：Radeon 部署与实验 | ROCm/后端适配、模型台账、离线依赖、显存与耗时测量、批量实验及统计。 | A 提供固定实验版本；B 复核评测结果。C 同时保留成功、失败、超时和环境异常，不只整理成功样例。 |

三人可各主责一个单元；两人可由一人承担 A，另一人承担 B+C；单人则按同一接口顺序执行，并优先削减候选模型数量与高级功能，而不是削减判定和复现。A需掌握B、C进度情况，同时进行决策。但在我们当前情况下，A应当由我来承担，同时我还会承担B/C的任务。

### 3.2 六周参考安排

| 阶段／参考窗口 | 主责；协作 | 核心交付 | 进入下一阶段的条件 |
|---|---|---|---|
| P0｜第 1 周前 2 天 | A；B、C | 规则矩阵、任务接口、未决问题与范围清单 | 关键阻断项明确；拿不到官方信息时，保守假设与风险已单独登记。 |
| P1｜第 1 周余下时间至第 2 周前段 | C、B；A | 可用本地推理服务、可信 EDA 验证链、环境锁定记录 | 真模型可运行；正确/故意错误 RTL 能被可靠区分；至少完成一次相近环境离线检查。 |
| P2｜第 2 周后段至第 3 周前段 | C；A、B | 合规基线、数据适配、开发/留出清单、模型初选 | 基线可复跑；数据和结果隔离；选型有实际容量、耗时及通过结果支持。 |
| P3｜第 3 周至第 4 周 | A；B、C | 自动生成—验证—修复闭环及失败分类 | 批处理无需人工修改；停止、回退和超时可控；已完成同模型前后对比。 |
| P4｜第 5 周 | B、A；C | 有回归依据的技能库、消融实验、预算配置 | 选择有证据支持的版本；不以单例改善代替整体收益。 |
| P5｜第 6 周 | A、C；B | 冻结容器、MODEL.md、REPORT.md、复现及完整证据 | 干净环境断网运行成功；资产校验一致；提交项和未解决问题逐项核验。 |

关键路径为 **P0 → P1 → P2 → P3 → P4 → P5**。P1 的推理部署与 EDA 校准可以并行；P2 的数据整理和 P3 的工具封装可以部分重叠，但不能在验证链不可信时开始比较通过率。报告素材从 P0 开始积累，第 6 周不再首次补记模型来源或重建实验历史。

最后一周不新增赛道或重写主架构，并建议保留其中最后 2—3 天处理阻断缺陷。正式期限较紧时，先减少模型横评、复杂检索和训练，不跳过同版本验证、基线审计和离线复现。（比赛过程中常会出现时间来不及的情况，如果最后三天还希望增加功能，则可以考虑使用git来保存锚定点，同时留出重新部署的时间）

## 4. 各阶段实施计划（这一部分可以暂缓，确认后分工后再实现）

### P0：确认规则、反馈权限与接口

**对应要求：R01—R07、R09—R11。负责人：A；B、C 会签。**

本阶段首先确认具体 Radeon 型号及显存、官方镜像与 ROCm 版本、CPU/主存/磁盘限制、题目输入输出格式、单题与总时间预算、EDA 可用与授权方式。另一项同等优先的工作，是明确智能体究竟能获得公开测试台、受限反馈接口，还是仅有题目文本；官方采用参考测试判分，并不自动等于队伍可以访问参考测试。

交付 `requirements.md`、`interface_spec.md` 和一份带负责人、截止时间的待确认清单。接口最少定义题目原文、顶层模块/端口、源文件形式、输出路径及可见测试资产；开发用 JSON 必须标为内部接口，不冒充官方标准。

**退出条件与处理办法：**反馈权限、提交入口和预算已确认，或为暂未确认项设计了可替换适配层。缺少隐藏测试访问权不是要求开放权限的理由，而是采用“自建测试辅助、官方判定分离”的模式；连题目接口和时间计量边界都未知时，先完成模块开发，不发布“已对齐正式环境”的结论。

### P1：打通 Radeon 推理与可信 EDA 链

**对应要求：R01—R04、R08。负责人：C（推理）与 B（EDA）；A 集成。**

C 按实际 GPU 与官方软件栈选择经过验证的后端，先用较小模型打通服务，再测试最终上下文和输出长度。Radeon 的兼容性需要核对具体硬件、ROCm、操作系统和后端版本，不能仅凭“都是 AMD 显卡”直接复制数据中心 GPU 的安装方案。vLLM ROCm 为首选验证路径；若不兼容，可评估 llama.cpp HIP 作为一种备选，不同时维护大量后端。[S1][S2][S8]

B 先不接模型，用手写计数器、状态机、组合运算等小任务校准 `xvlog → xelab → xsim → synth_design`，并注入语法、复位优先级、位宽或更新步长错误。测试判定同时检查完整执行、错误信息和测试依据，不能只搜索候选打印的“PASS”字符串；综合也须确认目标设计及实际输出。[S3][S4]

**交付与内部门槛：**环境清单、加载/峰值显存记录、固定 EDA 脚本、约 10 个人工样例及错误变体；正确与错误样例应全部按预期分类。使用目标长度的短、中、长请求连续运行，观察是否出现显存溢出、截断或进程遗留。数量只是内部校准建议，不是赛题门槛。

**主要问题与方案：**加载成功但长上下文溢出时，先减并发、删除非必要上下文和降低非必要运行开销，再评估量化或小模型；必须保留完整题意与输出余量。不得以跨卡或把超限模型部分放在 CPU 上规避单卡容量约束。工具缺失、许可证或器件库异常属于环境问题，应停止模型修复并由 B/C 排查。

### P2：建立真实基线和开发数据体系

**对应要求：R05、R08—R10、R12。负责人：C；A 实现入口，B 审查任务与判定。**

基线使用原题、同一推理服务与上下文配置，单次生成后结束；代码提取和外部评测不能把失败反馈送回模型。作为额外公平性控制，建议同步锁定模型权重、量化、输出上限和采样配置，保存原始请求。基线和智能体应在共同运行流程中产出，但冷热启动及成本如何计入最终分数，须按官方口径执行。

公开数据优先使用 VerilogEval v2，保存仓库版本与题目清单，将原有评测流程适配到指定 Vivado 版本，而不是把公开仓库的其他工具依赖直接带入正式判定。原题可以进入生成上下文，参考实现和保密评分资产不得混入提示词或技能库。[S0][S5]

首轮建议选取 30—50 道不同类型的开发任务进行部署及接口排错，再将未参与调参的任务作为固定留出评估；同类改写、衍生题应按设计来源分组，避免一份答案的轻微改写分散到开发与留出两侧。公开数据可能被预训练模型见过，报告只能如实说明限制，不能声称它一定是未见数据。

**交付与退出条件：**合规基线入口、数据清单、模型初选表、逐题分级结果和完整耗时。先比较少量可部署候选，容量、端到端结果、时间和来源均有证据后再定主模型；若结果异常地好或差，优先检查题目适配、测试泄漏和代码提取，而不是立即调整提示词。

### P3：实现反馈修复闭环

**对应要求：R03—R06、R09—R11。负责人：A；B 负责根因分类与反例，C 负责批量验证。**

将模型能力限制在候选生成与修复，把状态推进、工具调用、超时及保存交给固定代码。每次反馈只保留首个根因、相关代码、必要前态和期望/实际差异。工程等级区分“编译失败、编译通过、可信功能测试通过、功能与综合均通过”；没有功能证据时保持未知，综合成功只增加结构证据。

修复策略先采用简单规则：先局部修根因；新候选证据更差时回退到已知较好候选；完全重复、连续无改进、时间不足或达到轮数上限时停止。每次改代码都重新验证，不能沿用上一版候选的通过标记；最终输出哈希必须对应实际被验证的版本。阶段预算共享同一截止时间，并在发起新一轮前预留最终验证与结果落盘时间。

**交付与退出条件：**自动入口、结构化日志、错误分类器、停止/回退测试和同模型对比数据。系统需能连续完成开发集批处理，不靠人工修改中途候选、提示词或测试台。至少演练输出截断、重复候选、仿真超时、工具崩溃和“最后一次修复退步”等情形。

**主要问题与方案：**当工具判定稳定但修复没有净收益，先分析“新增通过题”和“被修坏题”的差异，缩小允许修改的范围或关闭低收益重试；不直接加更多角色、更多轮数。模型可以提出原因假设，但只有后续工具结果才能确认修复有效。

### P4：形成技能包，验证增益并压缩成本

**对应要求：R08—R12。负责人：B、A；C 执行对照实验。**

从已记录的开发失败提炼少量技能，优先覆盖复位、位宽与符号、逐周期延迟、组合完整赋值、状态机及参数边界。每张技能记录触发条件、错误模式、修复原则、反例和独立回归用例；技能是可迁移规则，不是开发题答案。检索先用关键词或 BM25 类稀疏检索，避免为了几十张卡增加额外显存和部署依赖。

只开展足以回答关键问题的实验：裸跑基线、仅智能体模板、模板加工具修复、完整方案四组，保持模型与题目清单一致。必要时只对不确定的技能做删除对照，不穷举所有组合。研究原理可参考反馈式硬件代码生成工作，但实际增益只能由本项目实测确认。[S6]

**交付与退出条件：**技能版本、形成记录、消融表、净增/净减题目、最终预算配置。先保证绝对成功率，再看相对自身基线增益和耗时；以固定留出评估结果检验泛化，不在看到留出失败后继续把它当“未见验证集”反复调参。

**主要问题与方案：**技能越加越多但收益下降时，减少检索数量、合并重复规则并移除无收益内容。推理快但总时间仍长时，检查 EDA 启动、综合、I/O 与重试占比；优先早停、复用常驻服务（须符合官方运行方式）和减少无效调用。更大模型或微调只有在主线稳定且有剩余时间时评估，不列为必做项。

### P5：冻结、断网复现与提交

**对应要求：R01—R06、R08—R12。负责人：A、C；B 独立复核判定证据。**

固定官方基础镜像来源、模型与分词器版本、量化产物、推理后端、提示词、技能、代码和配置；将所有可变输出放在独立目录。清单应覆盖实际运行资产，而不只是 Python 文件。冷启动时不依赖下载、已有用户缓存或手工设置；EDA 授权采用赛事允许的方式，不能假定断网环境仍能访问外部授权服务。

从干净工作目录进行端到端演练，同次产出基线与智能体结果，记录模型加载、生成、编译、仿真、综合和总墙钟时间。执行前后检查冻结资产校验和；进行一次由非主开发者按说明复现的演练。单人实施时至少另建干净环境重跑，不把原目录再运行一次视为独立复现。

**交付与退出条件：**容器及构建/启动材料、MODEL.md、REPORT.md、基线入口、技能包、原始数据、统计汇总和失败分析齐全。报告清楚区分真实模型和 EDA 实验、单元测试、模拟工具测试、估算与未验证事项。最后阶段发现性能退化时回退到已验证的冻结候选，不以临时人工修题替代自动流程。

## 5. 跨阶段高风险问题与处理决策

下表集中列出会影响路线成立的风险。各阶段的一般代码缺陷在日常开发中处理；这里要求一旦触发就明确负责人和降级方案，避免把所有问题都交给模型重写代码。

| 风险／触发信号 | 首选处置与保底方案 | 责任／赛题对应 |
|---|---|---|
| Radeon 后端不兼容：模型无法加载、特定算子失败、长请求溢出。 | 按实际 GPU 和官方栈复核；回退到已验证版本及小模型。仍需更换后端时只保留一种备选，并重新跑基线与显存测试。 | C；R02、R08 |
| 功能反馈不可得：正式环境仅提供题目。 | 将公开/自建测试与官方判定分离；从题意生成并固定辅助测试，先用错误变体验证检错能力。测试不足则输出功能未知，不制造通过记录。 | A、B；R04、R09 |
| 评测器假阳性：错误 RTL 也显示通过，或只输出 PASS 就被接受。 | 暂停通过率实验，校准结束条件、断言和判定来源；测试资产只读。判定链通过正反例验证前，不进行模型选型。 | B；R04、R10 |
| 修复循环耗尽预算：难题无限重试，最后无结果输出。 | 全局截止时间、子进程清理和预留输出时间；重复候选去重，低收益修复早停。优先交付已保存候选和失败原因。 | A、C；R09、R10 |
| 基线/统计不公平：基线配置不同，把五轮修复当 pass@5。 | 审计两类原始请求；重跑受影响对比。独立完整运行和内部候选分别编号，未确认的评分字段不强行填数。 | C、A；R05、R09、R10 |
| 技能或数据泄漏：技能记住测试答案，评测中资产被更新。 | 按来源分组划分数据；技能仅来自开发阶段归纳，评测期间只读。发现污染则剔除受影响结论并重新评估。 | B、A；R06、R11、R12 |
| 综合与时序概念混淆：有网表便宣称 5 ns 完全收敛。 | 分别记录综合状态、约束、时序报告与实现阶段；按官方阈值决定是否追加实现，不通过改端口或放松约束规避。 | B；R04、R10 |
| 正式细则或接口改变：基线计时、输入格式、工具权限与预期不同。 | A 做差异清单；先改适配层和统计，不临时改判定含义。影响冻结资产时在允许窗口内更新并重验。 | A；R01、R03、R05、R06 |

**取舍规则：**合规性或判定可信性出问题，先停止性能优化；只有速度问题时，优先缩减可选开销；只有难题失败时，保留失败分析，不默认扩大模型和搜索规模。高级检索、多智能体、微调与 HLS 扩展都不应挤占最终复现时间。

## 6. 实验、预算与阶段验收口径

### 6.1 用一套证据账本评价方案

每题保存题目 ID 与来源、运行 ID、随机种子、模型和配置哈希、候选哈希、工具版本、各阶段状态、测试来源、首个根因、峰值显存及时间。编译/仿真/综合状态至少区分通过、失败、未知/未运行；超时和环境异常另外分类，不悄悄从总样本中删除。

本地汇总先同时报告“相对全部任务的各级成功率”和“进入该阶段后的条件通过率”，并明确分母。最终加权总分待官方公式发布后计算。方案选择关注四件事：最终成功题数、相对自身基线的净增益、墙钟成本、可复现与可审查程度，对应 R09—R11。

对于 pass@k，公开代码生成评估常以独立样本定义成功率估计；比赛中是否把一次完整智能体执行视为一个样本，需要以官方说明为准。[S7] 项目从一开始分别记录“独立运行编号”和“内部修复轮次”，既不把五轮关联修复当作五次独立采样，也不把同一随机种子重复结果冒充多样性证据。

### 6.2 预算是完整运行预算，不只是模型生成预算

预算台账包括服务启动/模型加载、基线生成、智能体各轮生成、工具运行、排队与 I/O，以及总墙钟时间。哪些费用计入官方指标、基线是否共享单题额度、是否允许服务常驻，需要在 P0 确认；在此之前全部单独保留原始时间，避免后续无法重算。

每次新重试前检查剩余预算是否覆盖预计生成、所需验证和安全落盘。模型运行使用单卡，EDA 首版采用有界并发或串行，待 CPU、主存、工具资源和总耗时明确后再增加并发。不能仅根据 GPU token 速度判断整个系统效率。

### 6.3 阶段验收不等于获奖承诺

P1 验收解决“环境和判定链是否可靠”；P2 验收解决“基线是否真实”；P3 验收解决“系统能否自动闭环”；P4 验收解决“复杂度是否带来可重复收益”；P5 验收解决“别人能否在正式约束下复现”。没有收益时，可以保留较简单版本；不能为满足计划文字而把无收益组件强行合并。

## 7. 交付清单与实现者行动重点

### 7.1 最终材料由哪个阶段产生

| 交付项 | 形成阶段／主责 | 必须包含的内容 |
|---|---|---|
| 容器与推理服务材料 | P1 起，P5 定稿／C | 官方镜像来源、依赖及后端版本、离线资产、启动方式、设备与写目录约定。 |
| MODEL.md | P2 起，P5 定稿／C | 模型来源和版本、量化、实测显存、上下文；选型及放弃理由；微调时补充完整声明。 |
| agent/ 与运行入口 | P3 起，P5 定稿／A | 状态机、错误处理、预算、候选管理、官方接口适配；run.sh 与合规 run_baseline.sh。 |
| skill/ 与技能依据 | P4／B、A | 技能内容、来源失败、适用条件、回归用例、消融依据及版本。 |
| REPORT.md 与原始证据 | 全程，P5 汇总／A、B、C | 架构、选型、控制流、技能形成、实测、失败及复现；附逐题数据、环境和冻结记录。 |

本路线规划可以作为最终设计报告的“实施路线与工程组织”章节，但不能代替最终 REPORT.md 中的实测结果、模型选择记录和失败分析。完成一个阶段，就把对应证据写入材料，不在提交前根据记忆补造实验过程。

### 7.2 你需要优先掌握的知识

第一是 RTL 的复位、位宽、时序与状态机，能够判断模型生成的逻辑是否符合逐周期要求。第二是自检查测试台和 Vivado 批处理，能够区分“电路错误”与“测试/工具错误”。第三是 Python 进程管理、结构化日志、配置和版本控制，能够把一次成功演示变成可重复流程。第四是 Radeon 本地推理的基本部署与显存观测，能够看懂兼容性、上下文和量化带来的限制。

现阶段不把“会训练大模型”作为前置条件。与 AI 协作时，每次任务以“对应 R 编号、当前阶段、固定接口、失败证据、允许改动范围、验收条件”为输入；AI 负责协助实现和提出解释，人负责规则与测试边界，工具负责最终证据。不要让 AI 同时修改候选和判定标准来消除失败。

### 7.3 启动阶段最先完成的三件事

先确定具体 Radeon 型号、官方环境和反馈权限，形成 P0 台账；同时让 B 用手写正确及故意错误 RTL 校准真实 Vivado 链；随后让 C 跑通一个可部署的小模型并记录长短请求的实际显存和耗时。三项证据具备后，再由 A 合并成第一条自动生成—验证—修复记录。

**最终路线判断：不更换已有主线，补齐“谁负责、何时交付、什么算完成、失败后怎样处理”的工程约束。核心竞争力应当来自可信验证下的稳定增益，而不是流程图的复杂程度。**
