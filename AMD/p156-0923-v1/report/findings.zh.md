# 156 题实验结论与改进方向

## 结论先行

本次完成了全库 156 题的盘点、公开接口检查和校准处理；对接口可用的 155 题全部重新生成候选，对通过既定校准门槛的 149 题全部完成 Baseline/Agent 配对验证。不是 156 题均完成了有效评分，更不是 156 题均已修好。

冻结测试台原始成绩：Baseline 135/149（90.60%），Agent 146/149（97.99%），增加 11 题、7.38 个百分点。14 项初始失败中，13 项被策略允许进入修复，11 项最终被测试台判为 PASS。另 1 项在 Host 分类层就被拦截。

**不能将 97.99% 直接宣传为真实功能准确率。** 事后发现 Prob078 的稳态错误候选被测试台接受，Prob093 与 Prob149 的公开需求和参考实现存在明确矛盾。正负例校准只证明参考正例能过、指定负例不能过，未证明参考符合公开需求或采样点正确。

保留全部原成绩，仅做敏感性分析：排除上述三个已确认问题项后，剩余 146 题的 Baseline 为 135/146（92.47%），Agent 为 145/146（99.32%）。这是事后筛查，不是新预注册基准，也不保证其余题目没有问题。三项证据见 [修复轨迹与评测有效性](repair-cases.zh.md)。

## 候选非法或缺失的原因

155 道实际生成题中，133 道首轮通过接口/策略检查，22 道经纠正成功，最后没有遗留“接口可用但拿不到完整合法候选”的任务。唯一未生成的 Prob062 存在公开接口宽度冲突。完整分析见 [候选生成](generation-findings.zh.md)。

1. 21 个首轮响应只返回 reasoning，provider 达到 max-tokens，正文为零。问题不在于模型没运行，也不是本地缓冲提前截断。一次有界的 off 模式纠正均取得完整候选。
2. Prob031 两次返回输出 q，被错误的公开 input q 接口拒绝；最后成为空模块。该题始终校准阻塞，未把“格式合法”当作“功能已修好”。
3. Prob106 在候选接口检查后才暴露编译错误：wire 输出被过程赋值。合法性检查与编译合法性必须分开统计。

生成恢复增加了尝试机会。本批 149 个比较项中，130 个首请求合法，124 个首请求候选通过 Baseline；余下通过数包含候选恢复的贡献。因此主表不是严格单请求 pass@1，但 Baseline 与 Agent 仍共享完全相同的初始候选。

## 为什么 Agent 增益受限或成本偏高

**可修复机会有限。** Baseline 已有 135/149 通过，原始口径最多还能提高 9.40 个百分点。不能只看总体百分点，也要看 14 个初始失败进入了什么路径。全量后加入了更多状态机/串行协议问题，本批确实出现更明显的功能修复；不能直接与旧 100 题的 2 个百分点作因果比较。

**“通过”收益组成不同。** 11 个新增 PASS 中，7 个主要属于逻辑/时序修复（098、113、133、137、146、150、154），3 个主要是初值/复位适配（034、104、153），1 个是确认的采样伪增益（078）。这三类价值不能等同。

**高 reasoning 预算没有自动转化为行动。** 全批出现 65 次 provider max-tokens，其中 64 次只有 reasoning、没有正文或工具增量。修复阶段有 44 次强制动作恢复。Prob133 一题消耗 40/131=30.53% 的修复物理请求，先重复原候选 19 次才提出有效修改。增大 RTL 轮数无法解决这种模式。

**状态协议仍有脆弱点。** Prob093 在待验证时返回两个工具调用，被整体拒绝并结束；Prob078 在仅允许验证时仍调用编辑。拒绝违规动作是正确的，但一次格式问题就终止，或只返回 UNKNOWN_TOOL，恢复能力不足。

**归因和分类仍不一致。** Prob106 的诊断明确指向 DUT 且可修，却因 kind=unknown 被拦截。此处应扩充明确错误分类，不应为了提高分数放开未知环境错误。

**时间证据太短且未与采样事件对齐。** 三条时间戳结束值不足以解释多拍协议；Prob113 的报告失败时间与波形更新后输入不同，Prob133 返回文本反复猜测时钟相位。需要采样点证据，而不是让模型用猜测补齐历史。

**外部超时应单独核算。** Prob149 已从 1194/2040 改善到 601/2040，最后因单个模型请求 120 秒终止，且该题规格另有冲突。不能说“15 轮尝试后未修好”，也不能说“综合十分钟仍不够”。

## 改进优先级

| 优先级 | 改进 | 可验证的验收标准 |
|---|---|---|
| P0 | 修订题库协议而非掩盖缺陷 | 对七项校准阻塞及 078/093/149 单独版本化；正确实现通过，相关错误变体失败，刺激完整执行；旧结果不改 |
| P0 | 补齐 VRFC 10-1280 分类 | 106 的真实日志可进入修复；同编号但非 DUT 路径仍不能越过安全门槛 |
| P1 | 有界协议纠正 | 零/多调用与状态禁用工具能够纠正；不得部分执行违规多调用；纠正计入请求预算但不计 RTL 修改 |
| P1 | 重复候选策略切换 | 连续同请求哈希/同源码拒绝后切换一次策略或返回明确 STAGNATION；用离线回放与独立实测评估，不能直接把本轮后来成功的 133 截掉就声称改进 |
| P1 | 可靠的时序反例 | 从复位/进入相关状态到失败点保留有界历史，并在可信断言采样处记录输入、参考、DUT；禁止把时间戳末值当作精确采样值 |
| P2 | 分离生成策略和修复轮数实验 | 固定初始候选、模型和评测器，对 3/8/15 轮及不同推理策略分别消融，报告功能修复率、协议失败率、调用/token 成本 |

开源方案提供的是可借鉴机制，而不是能直接替换本项目协议的万能修复：SWE-agent 使用有上限的格式纠正循环；cocotb 明确区分边沿事件与稳定读取阶段。本次未引入新代理框架，优先沿用现有 Host、调用和 EDA 实现。[SWE-agent](https://github.com/SWE-agent/SWE-agent/blob/main/sweagent/agent/agents.py)；[cocotb Timing Model](https://docs.cocotb.org/en/stable/timing_model.html)。
