## 不合法或未完成候选的原因

**21 次是 provider `max-tokens`，而非本地字节缓冲提前截断。** 这 21 次的 `output.txt` 都为 0 字节，实际返回的 reasoning 为 16,201 至 33,411 字节，`response_complete=false`。不能因为 HTTP 请求成功或 reasoning 很长就认为已经生成 RTL。

相关题号为 030、070、082、086、089、093、094、098、113、116、133、135、137、139、140、146、147、149、153、155、156。每题均在一次关闭思考的纠正后得到通过接口/策略检查的完整候选。

以 Prob030 为例，归档的返回文本反复讨论线性加法与平衡树、位宽、genvar 复用及边界情况，但没有提交最终正文。该描述仅概括接口返回文本，不声称知道模型未公开的内部过程。[逐题调用记录](../analysis/Prob030_popcount255.md)

**另外 2 次是 Prob031 的接口冲突。** 两次完整输出把 q 声明为输出，与题面列出的 `input q` 不一致。第二次纠正后得到空模块，只满足错误接口，不满足 D 触发器功能。该题始终不计分；详见 [校准与题库分析](calibration-findings.zh.md)。

这说明必须区分三件事：响应完整、候选通过 Host 接口/策略检查、RTL 功能与综合验证通过。只优化第一、第二项，不能保证第三项。

## 本次修补起到的作用

- 不再把首个完整但接口错误的响应直接当终点；最多两次纠正，所有失败响应保留。
- 恢复请求携带不变的公开题面、Host 拒绝原因、上一轮返回的 reasoning 和输出，并明确将旧模型文本视作不可信草稿。
- 恢复实际使用 `reasoningEffort=off`、16384 输出 token、262144 响应字节；初次请求仍为 high/8192。
- 未把截断文本当作可执行 RTL；没有使用参考答案或仿真结果指导生成。
- 本批生成阶段没有遇到需要实测的部分传输恢复路径。该路径有聚焦回归覆盖，但不能用本批结果声称其真实网络故障恢复率已验证。

采用的是有界纠正思路，而非无限重试或引入新的代理框架。对应开源参考为 [SWE-agent 的错误纠正循环](https://github.com/SWE-agent/SWE-agent/blob/main/sweagent/agent/agents.py)。DeepSeek 文档也明确提示 JSON 模式仍可能返回空内容，不能把换成 JSON 当作充分修复：[JSON Output](https://api-docs.deepseek.com/guides/json_mode/)。

## 下一步应如何验证

1. 先阻止已确认的题面冲突进入生成恢复循环，避免为了满足错误接口而诱导空模块。修订题面必须另建可追溯版本。
2. 独立比较“初次 high + 有界 off 恢复”和“初次直接输出代码”的效果，报告调用量、输出截断率和最终四阶段通过率，而不仅是候选合法率。
3. 把模型返回文本中的长时间重复论证作为成本诊断信号，不把延长 reasoning 或增加 RTL 修改次数视为必然有效的解决方案。
4. 在后续实验中保留同一批初始候选，再比较 3 轮与 15 轮修复。本批重新生成了候选且同时修改恢复流程，不具备单独估计“增加到 15 轮”的因果效应的条件。
