# RTL Harness 联跑纠错

目标是让下一次联跑少走已经观察到的弯路，不是复述 RTL 编码常识。

本技能由 Codex 根据真实会话、工具证据和回归结果整理，不直接复制教师总结。部分控制器措施已有本地或真实联跑验证，具体范围见规则；这不等于已证明加载技能带来模型收益。技能是行为指导，不能替代控制器中可执行的预算、取消、权限和终止逻辑，也不会增加工具权限。

## 先判断问题发生在哪一层

1. 确认这是实际模型工具闭环：关联模型请求、工具调用、工具回传和下一次请求；把脚本模型自检与真实 API/EDA 结果分开。
2. 分别判断传输、Agent 回合、文件修改、验证阶段、总结接收和预算状态。不要从一个 `incomplete` 或退出码推断整道 RTL 的成败。
3. 只读取当前症状对应的 [联跑规则](references/patterns.json)，不要无差别加载历史完整会话、题目答案或含私有材料的溯源图。

## 按症状选规则

| 症状 | 规则 |
| --- | --- |
| 不清楚是否真正调用了模型或工具 | H01 |
| 响应截断，候选或工具动作可能不完整 | H02 |
| 多次写回相同文件，工具活动很多但没有进展 | H03 |
| 工具已报错或声称停止，下一步却仍继续 | H04 |
| 总结已接收，收尾请求却把会话变为失败 | H05 |
| 提示、配置、实际调用上限或阶段预留不一致 | H06 |
| 重启、续跑或上下文过长 | H07 |
| 教师叙述与真实编译/仿真/综合记录不一致 | H08 |
| DUT 与自写测试台相互矛盾，或测试只打印失败 | H09 |
| 要把教师总结整理成 skill | H10 |
| 涉及日志指令、私有评测、全局配置或技能加载 | H11 |
| 要汇总整批结果或宣称任务完成 | H12 |
| 自然查询未命中、匹配错义，或只加载规则却没有行动 | H13 |

## 模型与控制器的职责

- **Agent**：观察当前文件与诊断，说明下一次动作要区分哪个原因；不把原样写回计为修复，不用反复复述代替工具操作。没有新证据或可执行措施时，使用已提供的停止/交接方式，不编造取消工具。
- **Harness 维护者**：通过实际生命周期接口停止并等待回合、工具和子进程结束；返回工具错误或在提示里要求停止都不等于执行了取消。没有结束后的请求/进程证据，就不要声称守卫已生效。
- **总结者**：先核对工具结果再接受教师归因；把教师原文、开发者纠正、未隔离的原因和下一步建议分别保留。
- **检索使用者**：命中后核对条件并行动，不把反复换词查询当作进展。未命中不代表没有相关知识；错义匹配不可采用。已加载、实际送达、行动符合和新修复通过分别记录。

## 用什么判断完成

把以下状态分列，而不是压成一个“通过”：外部请求是否发生及结果是否已知、Agent 回合为何结束、总结是否被接收、最终源码是否有对应验证、是否因本地预算而未启动、哪些结论仍待确认。

若任务要求的总结及证据已接收，不应仅为一句礼貌收尾再消耗必需预算。结束条件必须由控制器明确支持；没有该能力时应报告限制，不能自行把原生回合状态改成成功。

交接时保留最后有效候选、最后验证所对应的源码/测试配置、未解决的问题和续跑所需授权。不得覆盖原始失败记录，也不得把这套指导当成已经修复 Harness 或已经证明 skill 增益。

若要验证新的纠错，起点必须是可追溯的原始错误候选；先复现失败，再检查本轮修改和最终验证。空白生成、旧候选复验、文字审查和评测口径争议不得计入同一修复成功分母。
