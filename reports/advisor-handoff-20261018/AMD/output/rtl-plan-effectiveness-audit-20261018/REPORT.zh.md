# 规划与修改有效度离线复核

日期：2026-10-18。复核对象为上一轮七题 skill ON/OFF 的全部 18 份规划、44 次编码器调用和 23 次既有 EDA 验证。本轮新增模型调用 0 次、新增 EDA 运行 0 次，没有修改运行时、skill 或题目答案，也没有重跑云端模型。

## 结论

已有输出没有证明模型能稳定完成“有效规划、遵守约束、被拒绝后调整策略”。主要问题已经不只是技能是否送达，而是：规划存在无效或含糊的修法；编码器没有落实计划中的关键修改；收到明确拒绝后仍会重复同一方案。

“规划有实质修改”也不足以作为通过条件：18 份中有 16 份提出代码层面的变化，但只有 6 份经逐条复核属于针对当前根因的合理方向。这 6 份仍不是完整正确性证明，实际落实要看补丁和 EDA。完整规划、原输出路径与逐项判断见 [规划复核记录](plans.json)。

## 规划是否有效

| 复核项 | 结果 | 含义 |
| --- | --- | --- |
| 包含实质变化提议 | 16/18 | 不等于能修好，也不等于变化必要 |
| 只有原样替换 | 2/18 | Prob142 ON/OFF 的全部 changes 都是 A 变 A |
| 根因方向合理 | 6/18 | 仍有非必要修改，编码器也可能不落实 |
| 声明位置等执行细节含糊 | 5/18 | 尤其未说明在 ANSI 端口处修改，还是额外声明 reg |
| 明确错误方向 | 5/18 | 2 份扩大固定输入宽度，3 份仍使用冲突的 enum 编码 |

16 份未提出公开端口宽度/方向变化，不能因此全部算作有效规划。以 reg/logic 修复输出变量类型可以保持公开接口，但放错位置仍可能产生语法错误或 ANSI 端口重声明。

### Prob096：有变化，但状态编码约束不成立

ON 规划提出 `S4 = 2'b01`，OFF 两份规划分别提出 `S4 = 2'b11`、`S4 = 2'b01`。这些值已经由 S1 或 S3 使用。初稿有五个 enum 成员，基础类型只有两位，容量为四，三个规划均未解决容量和唯一性约束。

规划的 checks 虽写着“编码唯一”，changes 却仍制造重复值。这是计划内部不一致，不是编码器单方面破坏了正确计划。上述算术检查绑定初稿 SHA 和原始代码片段，未把通用文字扫描冒充完整 SystemVerilog 类型求解。

### Prob142：引用正确，但没有实质修法

两组原始规划均包含以下形式：

```text
Change logic [1:0] state_reg; to logic [1:0] state_reg;
Change assign current_state = state_reg; to assign current_state = state_reg;
```

前后文本没有变化。enum 类型错误仍未得到解决，不能因为 cause 正确引用了报错行就判定规划有效。编码器随后两组都没有提交 edit_dut，而是重复 verify_rtl 未修改的失败版本。

### Prob104：变化明确，但违反固定接口

ON 规划直接写了 `Change q_in from a 1-bit input to a 3-bit input`。OFF 同样提出把 input q_in 扩成三位。可信题目接口规定它是一位，因此该方向在编码前已经不成立。

编码器 6 次修改提交中，5 次在精确应用后被既有接口校验拒绝，另 1 次引用了未被接受候选中的表达式，当前源码并不存在该锚点。这不是 EDA 未接受合法接口修复，而是候选违反接口或没有正确使用当前源码。

## 编码器修改的有效度

| 层级 | 数量 | 判定依据 |
| --- | --- | --- |
| 修改提交 | 28 | edit_dut 的真实模型工具调用 |
| 能精确还原候选 | 19 | 唯一锚点、版本一致、替换不重叠 |
| 无法应用 | 9 | 6 次缺失/歧义锚点，3 次完全不变候选 |
| 候选通过固定接口解析与检查 | 11 | 另外 3 次 ANSI 声明语法不受支持，5 次公开端口不一致 |
| 实际被 Agent 接受 | 9 | 另 2 次为已有拒绝版本的重放，不重复接受 |
| 通过本地 RTL 四阶段 | 4 | Prob060 ON/OFF、Prob039 OFF、Prob119 OFF |
| 接受后仍无进展并回滚 | 5 | 真实 EDA 仍失败，不是成功修复 |

9 个接受的候选都改变了代码 token，但其中 5 个没有修复当前阻塞错误。这说明“不是原样提交”和“工具接受”都不能替代有效度判断。

五个无进展候选分别是：Prob096 OFF 两次仍重复 enum 值；Prob119 ON 只改 always 形式、没有落实 reg 输出声明；Prob058 ON 添加了重复时序块却未修输出类型；Prob058 OFF 在模块体重声明 ANSI 输出，新增 VRFC 10-9336 错误。

一个明确正例是 Prob060：两组编码器只将畸形复位字面量换成合法零值，随后实际编译、展开、仿真、综合通过。另两个通过题包含额外赋值形式变化或注释，所以不能一概宣称全部成功补丁都为严格最小修改。

完整 28 次修改参数、对应规划、主机接受/拒绝和 EDA 结果见 [44 次编码调用记录](submissions.json)。这里的“通过”是开发环境 RTL 四阶段，不是比赛完整网表验收。

## 被拒绝后是否改变策略

本次区分工具立即拒绝与 EDA 失败后回滚。26 次工具拒绝中有 17 次还能观察到后续编码请求，另外 9 次已在任务末尾，不能假设模型本来还会如何处理。

| 17 次工具拒绝后的实际后续 | 次数 |
| --- | --- |
| 完全相同的工具和参数 | 8 |
| 回到相同代码或此前已拒绝代码 | 3 |
| 改了提交，但仍被拒绝 | 5 |
| 提交不同且被接受的修改 | 1 |
| 最终形成 RTL 四阶段通过的恢复 | 0 |

唯一“不同且被接受”的后续是 Prob058 ON 添加重复时序块，之后 EDA 仍失败。因此不能把 1 次接受误报为策略恢复成功。5 次 EDA 失败回滚中有 4 次可观察后续，也没有一次恢复为 RTL 四阶段通过；其中 Prob096 OFF 只换了注释措辞，候选代码 token 与上个失败版本一致。

### 拒绝信息并没有整体丢失

17/17 次工具拒绝后的请求，都能在真实 HTTP 内容中确认结构化反馈：6 次通过匹配 tool_call_id 的 tool 消息，11 次通过压缩请求的 `previous_tool_result`。4/4 次 EDA 回滚后续请求也包含对应候选身份和回滚结果。

原始 `adaptations.json` 的 `feedback_delivered_to_matching_tool_call` 字段特意只统计精确 ID 的 tool 消息，因此其计数为 6，不是“只有 6 次收到反馈”。补充投影审计覆盖另一种合法通道，最终送达数为 17。压缩后的显式上一动作字段没有 tool_call_id，使用工具名、接受状态、错误或候选身份关联，不把它声称为精确 ID 匹配。

例如 Prob104 OFF 被拒后，下一请求中的真实反馈是：

```json
{"error":"INVALID_OUTPUT","detail":"Ports disagree with trusted task interface"}
```

编码器仍反复提交扩宽输入的方案。因此至少在这些记录中，问题不能简单归因于“没有告诉它接口不符”。对于锚点错误，原反馈只有 PATCH_ANCHOR_NOT_UNIQUE，未指出第几项、缺失还是重复；这是可以改进的反馈精度，但不能据此保证模型一定能恢复。

证据：[拒绝/回滚后续逐项记录](adaptations.json)、[真实 HTTP 反馈投影](feedback-projection.json)。

## 规划与编码之间的差距

Prob119 ON 第一份规划已经提出 `output reg out`，编码器实际只把 always @* 改成 always_comb，遗漏修复根因所需的输出变量声明。Prob058 OFF 第一份规划明确要求在 port declaration 修改，编码器却在模块体新增 reg，触发 ANSI 重声明。这两个例子说明：即使规划方向合理，也必须核对候选有没有落实关键改动、有没有换成另一种无效操作。

Prob096 ON 则同时存在两层问题：规划给出冲突值；编码器又选择另一冲突值，额外改变输出置位条件，并使用出现两次的 `next_state = S4;` 锚点。它不是最小修改，也不能说“严格照正确计划修复但工具太苛刻”。

## 本轮完成的验证及限制

新增离线正负测试 21 项，覆盖原样/注释重放、token 边界、固定端口与类型限定词、枚举容量与重复值、锚点原子拒绝、接受与功能恢复的区别，以及普通/压缩反馈通道的正负关联。21 项全部通过。这些是审计逻辑的测试，不是新增的真实模型成功次数。

规划方向的 18 项判断是逐条人工式证据复核，由 Codex 给出，按 plan SHA 绑定；没有实现一个能理解任意自然语言计划的通用验证器。代码 token 指纹仅检查去除普通注释和空白后的重放，不证明语义等价或全局最小性。数值容量满足也不代表状态机功能正确。

本轮没有加入新防护后再调用模型，因此只能回答“现有输出表现怎样”，不能宣称“新防护已经让模型改善”。原工程、题库和封存交接包的前后检查，以及全部审计输入哈希和证据链接，见 [核验回执](verification.json)。

## 后续应验证的验收条件

1. 规划阶段：至少一项真正改变当前代码；明确修改位置；不得更改可信端口；enum 修法必须同时满足基础类型、容量和唯一性约束。保留“不确定/不能判定”，不要把引用行或关键词命中当成有效证明。
2. 编码阶段：接受候选前核对关键规划变化是否已落实；拒绝时指出违规端口，或具体锚点条目、出现次数和位置，不替模型补写答案。
3. 恢复阶段：对同一源码、相同失败反馈下的重复代码指纹做检查；单纯换注释不算新策略。恢复成功必须由新的 EDA 进展或通过证明，不能只看新参数或工具接受。

这些是后续实验的待验证条件，不是本轮已经接入 Harness 或得到真实模型验证的功能。应先在独立副本补离线控制，再单独冻结新实验，不能改写本轮负结果。
