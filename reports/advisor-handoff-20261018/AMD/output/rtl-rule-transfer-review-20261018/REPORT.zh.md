# 八个新例子的技能开关对照与离线改进报告

日期：2026-10-18。对象：项目组及博士生。范围：本轮 8 个新建 RTL 修复探针、16 个配对运行；以已有真实模型输出、HTTP/SSE 调用记录、工具动作及本地 EDA 日志为依据。本次仅离线复核和撰写报告，没有重新调用模型、连接云端或修改答案。

## 一 主要结论

**本轮没有证明新 skill 提高了修复能力。** skill ON 有 4/8 通过本地编译、展开、仿真、综合四阶段，OFF 为 6/8，分别为 50% 和 75%，ON 低 25 个百分点。共同成功 4 题、共同未通过 2 题，仅 OFF 成功 2 题，没有仅 ON 成功的题目。样本小且每题每组只运行一次，不能将这一结果推广为 skill 普遍有害，也不能据此观察模型内部是否“理解”。

当前瓶颈不是单一的“模型看不懂报错”：容量题在 Host 路由就被挡住；多项诊断方向正确但规划违反格式；另有一个最终成功的规划仍包含错误解释和无效修改项。因此必须分别衡量**诊断准确、规划合规、实际编辑、EDA 通过和拒绝后恢复**，不能用其中一个替代其他指标。

**建议暂不把此版 skill 作为已验证增益版本推广。** 保留它作为候选知识资产，先离线修复路由、拒绝定位及规划检查，后续再冻结新版本并做真实模型同期对照。本报告中的改进项尚未实施，不改算本轮成绩。[原始同期汇总](../rtl-rule-transfer-probes-20261018/comparison-summary.json)；[本次逐条复核证据](EVIDENCE_REVIEW.json)。

## 二 实验范围与有效性

- 模型：同一套 `qwen3-coder-30b` 规划器和 `siliconmind-qwen3-8b` 编码器，temperature=0、top_p=1、thinking 关闭。
- 对照：两组都保留 Harness、规划器、工具和约束检查，只切换技能加载。**OFF 是技能消融组，不是原始裸 Baseline**；本轮没有运行原始裸 Baseline。
- 配对：每题初始错误源码哈希一致，使用相同规格与本地评测资产，ON/OFF 顺序按题交替。题目是在本地已有技能及探针历史之外新编写，不能证明模型预训练未见过相似内容。

## 四 从输出和调用日志定位原因

### Probe201 模型之前的路由缺口

两位基类型容纳六个隐式枚举成员，展开产生 `VRFC 10-8928` 越界、`10-3279` 重复值及 `XSIM 43-3322` 后继摘要。两组都以 `UNCLASSIFIED_FAILURE` / `POLICY_BLOCKED` 停止，规划与编码调用均为 0。

**归因：Host 诊断分类及准入组合未覆盖，不是模型修复失败。** 应离线重放这组真实诊断，验证可信 DUT 主错误与同一 invocation 的后继摘要可以正确关联，同时继续阻断 TB、环境错误和来源不明的错误。不能简单把“全部未知错误”开放给模型。[ON 原始结果及 EDA 位置](../rtl-rule-transfer-probes-20261018/campaign/arms/on/compare-Probe201_six_phase/result.json)。

### Probe203 类型方向正确 但恢复没有改变修改策略

ON 两次都指出命名 enum 与普通向量的类型身份不同，提出统一声明类型；但 `before/after` 包含两行，违反当前解析器对字符串中 CR/LF 的禁令。恢复保留同一修改，只给 checks 增添标点，未交编码器执行。故障发生在规划协议，而不是已执行 RTL 的语义验证。

OFF 首次也有多行片段且 cause 超长，恢复改为单行 `command_t'(stored_state)` 转换，之后编码与 EDA 均通过。这是本轮真实的规划策略调整正例，但发生在 OFF。[ON 首次原文](../rtl-rule-transfer-probes-20261018/campaign/arms/on/plans/Probe203_typed_toggle/42ec76ad3ca6092c5473f8692c946cb2d937e2370e281c302571e95f330a922a/run-fUFuqk/output.txt)；[ON 恢复原文](../rtl-rule-transfer-probes-20261018/campaign/arms/on/plans/Probe203_typed_toggle/42ec76ad3ca6092c5473f8692c946cb2d937e2370e281c302571e95f330a922a/run-015MDv/output.txt)。

### Probe205 识别了过程赋值问题 但没有缩到限额内

ON 两次都提出把现有 `parity` 输出声明改为可过程赋值的 `reg`，方向与 OFF 的成功修改一致。原文测得 cause **首次 297 字符，恢复 223 字符，限制 160**。模型确实缩短了解释，但仍不足以通过；两次输出都完整，没有截断或网络异常，ON 因而没有编码调用。

**复核纠正：旧报告把 223 和 297 的先后顺序写反，不能继续表述为“恢复后反而更长”。** 旧报告保留，新结论以原文为准。OFF cause 为 147 字符，同方向编辑实际通过。[ON 首次原文](../rtl-rule-transfer-probes-20261018/campaign/arms/on/plans/Probe205_packet_parity/872ac47314bcdaa1834226313745f96d7271740300b758626ac7089b049190f4/run-wjx1Yo/output.txt)；[ON 恢复原文](../rtl-rule-transfer-probes-20261018/campaign/arms/on/plans/Probe205_packet_parity/872ac47314bcdaa1834226313745f96d7271740300b758626ac7089b049190f4/run-TySJR8/output.txt)。

### Probe206 两组都定位多驱动 但没有形成可执行规划

初始 `pulse_reg` 同时由时钟过程和组合过程写入，报 `VRFC 10-3818`。两组均提出移除组合驱动，保持注册输出时序，但首次及恢复的替换片段都含换行，均未进入编码器。OFF cause 是首次 201、恢复 98 字符；它解决了长度问题，仍未解决换行问题。旧逐例报告关于 OFF 恢复“增至 201”的说法也应纠正。

方向合理不等于已修好，未执行的候选不能计成功。ON 初次 checks 还把 `assign pulse=pulse_reg` 与写入者的描述混在一起，而这条语句读取 `pulse_reg`、驱动的是 `pulse`；知识库需要准确区分读者与写者。恢复的 checks 更准确，但修改片段未变。[两组原文、长度与恢复标记](EVIDENCE_REVIEW.json)。

### Probe208 成功结果掩盖了错误解释和规划检查缺口

ON 规划原文声称三个枚举值被放进 `a 1-bit type`，但它自己引用的声明是 `logic [1:0]`，宽度为两位，三个成员容量合法。规划第一项的 `before` 与 `after` 逐字相同，第二项才把 `marker` 比较从 MIDDLE 改到 LAST。该规划竟被记为 valid。

编码器先提前验证被拒，随后只提交 marker 的实际修改，**没有提交枚举 A-to-A 项**，最终四阶段通过。这证明有效改动得到执行，不证明错误诊断正确。当前 `exactEdit` / `guardRepair` 检查最终候选是否整体改变，没有逐项禁止混在有效编辑中的 A-to-A；这是与提示词“no A-to-A changes”不一致的检查缺口。

**“10 个候选与规划一致”应限定为最终源码净效果一致，不是每条替换逐字照做或每条诊断正确。** 新 skill 已说明枚举容量规则，但 ON 仍在合法边界例误触发解释；可能是规则过度套用，尚不能仅凭这次运行确定提示内容是唯一原因。OFF 直接定位 marker 条件错误。[ON 规划原文](../rtl-rule-transfer-probes-20261018/campaign/arms/on/plans/Probe208_valid_capacity/b4bc5cdf0f9dbb00f1bcf7a06f0f95e821ed5682ca7b2e000f6b96bde0709d33/run-95inlH/output.txt)；[实际编辑调用](../rtl-rule-transfer-probes-20261018/campaign/arms/on/compare-Probe208_valid_capacity/models/run-dt6Bk0/model.json)；[检查器源码](../../workspaces/rtl-rule-transfer-probes-20261018/rtl-tools/src/phase1/p10-repair-guards.ts)。

### 共同问题 拒绝信息不够具体

20 次规划中 10 次有效、10 次无效。无效的 9 次存在格式问题，另 1 次是源码引用不合规。6 次规划恢复的 system 提示均含 `Host rejection details: []`，没有指出哪个字段、实际长度、限额、换行位置或缺失的引用。ON skill 确实明示了字符串禁止 CR/LF，模型仍未遵守；但 OFF 的通用修复格式提示也没有完整明示这个隐藏在解析器中的限制。

格式拒绝和引用拒绝应像锚点拒绝一样输出明确位置。这里同时有模型受限执行不足与 Host 反馈不足，不能全归为“胡乱修改”。另外，强制 cause 复述整行源码与 160 字符诊断上限在长源码行上有潜在冲突，需离线做可满足性检查；本轮 OFF 在同样约束下能够成功，不能据此把本轮全部失败认定为不可解。[规划器源码](../../workspaces/rtl-rule-transfer-probes-20261018/rtl-tools/src/phase1/p10-planner.ts)；[格式解析器](../../workspaces/rtl-rule-transfer-probes-20261018/rtl-tools/src/phase1/p10-plan-format.ts)。

### skill 与知识图谱的具体修订方向

不要继续堆积长篇解释或为 8 题写答案模板。把知识分为语言规则、规格契约、Host 协议和运行环境四类，每条记录明确前提、可观察事实、违反的关系、反例、最小修复方向、验证方法及适用边界。

- 枚举容量：先从实际范围计算 `abs(msb-lsb)+1`，再检查成员数量、值范围与唯一性；只有前提违反才触发。加入“三成员两位合法”的反例，不能看到 enum 就扩大位宽，更不能改动规格固定编码。
- 类型身份：相同位宽不等于相同命名类型；检查两侧声明和合法状态，再决定统一类型或显式转换。简短诊断与具体替换分开，不复制整段解释占满 cause。
- 驱动所有权：记录“哪个进程写哪个信号”，区分 RHS 读者与 LHS 写者；去掉冲突驱动仍必须保留规定时序，不能把删除任意过程当通用答案。
- 规划协议：不止写“遵守限制”，还给出字段与限制的机器可检查对应关系。拒绝后只针对实际错误位置调整，不靠更换 checks 标点或重述 cause 规避。
