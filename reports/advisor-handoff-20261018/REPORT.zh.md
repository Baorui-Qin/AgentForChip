# AgentForChip 阶段进展与技术创新方向汇报

汇报日期：2026 年 10 月 18 日  
汇报目的：梳理当前实现与实验发现，回应“AI 具体在哪里失败”，讨论后续可实现、可验证、可展示的研究主线。  
材料范围：项目源码、冻结实验汇总、模型与工具轨迹、独立复核报告及已有演示入口。本报告未新增模型调用或 EDA 实验；涉及后续工作的内容均为建议，不作为已完成成果。

## 一、汇报摘要

目前，AgentForChip 已不只是“调用模型生成 RTL，再启动 EDA”的原型。项目已经具备专用规划与修复流程、真实 EDA 分级验证、受约束的局部修改、失败回滚、技能加载，以及能够关联源码版本、模型请求、工具动作和验证结果的证据记录。

但当前最需要如实说明的是：**我们已经验证了部分工程机制，并收集到了有分析价值的失败轨迹；尚未证明现有 skill 能稳定提高小模型修复能力，也尚未完成当前双模型方案的正式赛事环境验收。** 最新八个新建修复探针中，skill ON 为 4/8、OFF 为 6/8 本地 RTL 四阶段通过，没有 ON 独有成功题。不能把“技能成功加载”“图谱已经建立”表述为“能力已经提升”。

结合师兄此前提出的“把失败拿出来，逐条分析为什么失败、AI 陷在哪里”，建议将后续主线收敛为：

> **面向资源受限 RTL 生成与修复，从真实失败轨迹中提炼带适用前提和反例的修复规则，以契约约束的局部修改和独立验证，研究智能体能否减少错误修复与无效循环。**

这条主线的价值不在于增加几个 Agent 或多接几个工具，而在于回答三个可检验的问题：

1. 哪些失败来自硬件语义，哪些来自规划、执行协议、Host 或评测环境？
2. 从失败中提炼的规则，是否能帮助模型处理未用于规则编写的新题，并避免在合法情形下误用规则？
3. 系统收到拒绝或反例后，是否能产生有实质进展的新修改，而不是反复检索、重复提交或仅改注释？

### 3.2 当前通过率不能当作正式比赛成绩

近期双模型实验使用本地 Vivado 2026.1。50 题中的 24 个四阶段通过候选，被固定为 2025.2 的网表库哈希校验阻断；八个新探针则没有校准的综合后网表验收 profile，十个四阶段通过运行仍为 `NETLIST_NOT_CALIBRATED`。

因此应分别报告“RTL 四阶段通过”“完整网表接受”“环境或校准阻断”，不能把环境阻断一律算成 RTL 功能错误，也不能将它们计为正式通过。

仓库 9 月 13 日赛题纪要记录了 Vivado/Vitis 2025.2、AMD Radeon/ROCm、单张 32 GB GPU、断网运行，以及同模型裸跑 Baseline 等要求。**当前方案尚无完整的相应合规证明；比赛要求仍需以赛事最新正式文件复核，本报告不将内部纪要视作新的官方确认。** 特别是，云端双模型开发成功，不证明两套模型、KV cache 和推理运行时能在目标单卡上共同满足资源限制。依据见[赛题纪要](AMD/competition_requirements(1).md)和[50 题网表环境审计](AMD/output/cloud-agent-questions50-20261017/netlist-environment-audit.json)。

## 四、回应师兄的问题：AI 具体陷在哪里

### 4.1 不能把所有失败都归为“模型不懂硬件”

| 失效层次 | 已观察到的例子 | 可以确认的判断 |
| --- | --- | --- |
| Host 路由 | Probe201 的枚举越界、重码与后继展开摘要组合未被修复准入接受；两组模型调用均为 0 | 是 Host 覆盖缺口，本例不能评价模型的枚举修复能力 |
| 规划协议 | Probe203、Probe206 方向合理，但替换字符串含换行，被当前格式协议拒绝 | 方案未执行，不能当作已修好，也不能直接当作已执行电路的语义失败 |
| 输出约束执行 | Probe205 ON 已定位过程赋值目标问题，cause 从 297 缩至 223 字符，仍超过 160 上限 | 有缩短动作但未达约束；本次没有编码调用。应采用复核后的顺序，不沿用旧报告的反向描述 |
| 硬件约束推理 | 历史 Prob096 为五个枚举成员分配两位编码，提出的新值仍与其他成员冲突 | 定位到重码不等于解决容量、范围与唯一性；规划的 checks 与实际 changes 可以互相矛盾 |
| 规格契约 | 历史 Prob104 将固定一位输入扩成三位，试图消除标量索引错误 | 编译方向可能变得容易，但违反题目接口；必须保留公开契约 |
| 规划与执行脱节 | 历史 Prob119 的规划要求修改输出变量声明，编码器却只修改 always 形式 | 规划合理也不能代替实际补丁核对与 EDA |
| 规则误触发 | Probe208 ON 将合法两位、三个成员的枚举误说成容量不足；规划还含 A-to-A 项，实际只改 marker 后通过 | 功能修复成功不能反证每条解释正确；候选整体变化检查不能替代逐项规划检查 |
| 知识使用停滞 | 教师线 Q123 最新小步观察在检索后重复读取已知文件，没有修改或验证 | 送达和引用规则不等于采用规则，不能仅靠增加检索内容解决 |

这些例子说明，我们需要分开评价：**诊断是否有依据、规划是否合规、修改是否落实、是否保持契约、EDA 是否通过、拒绝后是否真正恢复。** 不能用某一项替代其他指标，也不能由一次外部行为直接断言模型内部是否“理解”。

证据见[八题逐条复核](AMD/output/rtl-rule-transfer-review-20261018/EVIDENCE_REVIEW.json)和[历史规划与修改有效度审计](AMD/output/rtl-plan-effectiveness-audit-20261018/REPORT.zh.md)。

### 4.2 恢复失败既有模型问题，也有反馈问题

在历史七题有效度审计中，17 次可观察后续的工具拒绝，都能在下一真实请求中确认反馈送达；其中 8 次仍使用完全相同的工具与参数，只有 1 次产生不同且被接受的修改，但最终仍未通过 RTL。因此，不能一概解释为“模型没有收到反馈”。

另一方面，最新八题的六次规划恢复提示均出现 `Host rejection details: []`，未指出超长字段或换行位置。20 份规划中，10 份无效，包含 9 份格式问题和 1 份源码引用问题。这里又确实存在 Host 反馈不具体的缺口。

合理的后续目标不是简单“让模型再试一次”，而是：**让拒绝信息定位到可执行的具体错误，并检查下一动作是否改变了失败策略。** 最新八题中，ON 两次提前验证被拒后都转为有效编辑并通过；但规划恢复为 ON 0/3、OFF 2/3，不能将不同层次的恢复能力混为一谈。

### 4.3 验证本身也可能漏掉关键硬件行为

教师线曾出现 Q123 冻结测试通过，但独立容量检查发现第三笔写入便被阻塞，未达到声明容量 4。另有模型自写握手测试台违反阻塞期间数据保持约定的情况。开发者补验可以确认某个候选的有限行为，却不能回填成 Agent 自主完成的闭环。

因此，失败分析还必须追问：**究竟是 DUT 错、测试台错，还是验证覆盖不足？** 不能因为工具输出 PASS，就把相同来源的模型解释、DUT 与测试台相互印证当作充分证据。具体反证见[教师线五条失败路径报告](AMD/output/rtl-api-distillation-20261017/agent-knowledge-04/RUN_REPORT.md)。

## 五、建议聚焦的创新主线

以下是待验证的研究方向，不是已经成立的原创性或性能结论。建议以第一项为主线，第二项作为实现机制，第三项作为可信验证方法，不同时扩展三个大系统。

### 5.1 主线：从失败轨迹提炼“有前提、有反例”的修复规则

不建议把路线表述为“提取大模型隐藏思维链”。更准确、也更可复现的做法是：利用公开可见的简短诊断、实际补丁、工具反馈和人工审查，提炼条件化经验。当前相关教师开发记录也不应被表述为权重蒸馏或微调。

每条规则最少回答：

| 字段 | 需要记录的内容 |
| --- | --- |
| 适用前提 | 哪种语言结构、诊断来源与公开规格条件下可以应用 |
| 可观察事实 | 当前源码、位宽、成员值、驱动进程或握手事件，而非模型自称的原因 |
| 修复约束 | 哪些关系必须改变，哪些接口、编码和时序含义必须保持 |
| 合法反例 | 外观相似但不满足触发条件的情形，防止扩大位宽等过度修复 |
| 验证方法 | 编译或展开检查，以及针对容量、背压、边界参数等性质的独立验证 |
| 证据与状态 | 来源 hash、已测试范围；区分候选规则、离线已测和真实模型迁移已测 |

以枚举为例，不应只写“枚举有问题时检查位宽”，而应同时检查容量、值范围与唯一性，加入“两位三个成员合法”的反例，并保留规格固定的状态编码约束。Probe208 已说明：即使规则进入请求，模型仍可能误用，因此反例也必须进入评价，而不是只展示能被修好的正例。

**研究价值：**将经验从“若干提示词”变成具有适用边界和可追溯证据的资产。真正的贡献仍需由新题上的规则应用准确率、误触发率和最终修复收益证明，而不是由规则数量证明。

### 5.2 机制：契约约束的可执行局部规划与具体拒绝

项目已有精确替换、固定接口、有限枚举检查和版本绑定基础，不需要另起一个大型多智能体框架。建议优先补齐已暴露的问题：

1. 将短诊断与源码引用分开表达，避免完整长行引用挤占诊断长度；代码字段的多行能力与精确编辑工具保持一致，协议变更单独版本化。
2. 拒绝信息返回字段、条目索引、实际长度、限额、锚点匹配情况等，避免仅返回空数组。
3. 检查每一项替换是否有实质变化，不能让 A-to-A 混在有效修改中通过；同时保留候选整体重复与接口检查。
4. 核对关键规划变化是否真正进入候选；对未知 HDL 形式明确保留 unknown，由真实 EDA 决定，不能无限堆叠正则冒充语言前端。
5. 将“重复动作”“候选有变化”“EDA 阶段进展”“最终通过”分别记录，验证是否能够减少无效循环，而不只是在失败前更早拒绝。

**可展示价值：**清楚展示系统为何拒绝一次修改，以及后续是否形成满足契约的新修改。Host 负责检查和反馈，不替模型生成答案；规则辅助决策不等于确定性检查本身的收益。

### 5.3 验证：针对硬件特性的独立反例与边界检查

不建议立即铺开任意 RTL 的自动形式证明。可以先选三类已有失败证据、也容易构造明确判据的性质：

- 枚举容量、编码范围及唯一性，以及合法容量边界上的不误修。
- ready/valid 的阻塞稳定性、沿前握手和逐事务计数，避免漏计或重复消费。
- FIFO 声明容量、满空边界、回绕和非二次幂参数，不能只验证默认配置。

正确对照、初始错误种子和功能变异负例应在实验前校准；独立测试必须依据公开规格，不能复制 DUT 的同一段错误逻辑。评价用测试与参考实现不进入求解模型上下文。开发诊断与冻结评分结果冲突时保留原记录，另行裁定和版本化，不现场修改标准以凑通过。

**可展示价值：**不仅展示“修过了”，还展示“为什么值得相信这次修复”。有限检查必须注明范围；数字仿真不能证明物理 CDC 安全。

### 5.4 哪些内容暂不作为主创新

“更多 Agent 分工”“知识图谱界面”“更长提示词”“简单接入更多 EDA 工具”可以是实现手段，但不足以单独构成贡献。PPA 优化和全面形式验证可以后续探索；当前应先稳定正确性和实验口径，不能为了答辩覆盖面牺牲可完成性。

相关工作也已经覆盖部分基础思路：AutoChip 研究 EDA 反馈下的迭代生成与修复，RTLFixer 使用检索与 ReAct 进行语法修复。因此，“EDA 闭环”“RAG 修复”“组合大小模型”本身不宜直接声称为原创。我们需要进一步证明的差异，是**失败归因、条件与反例、契约保持，以及拒绝后的有效恢复在受限预算下形成的增益**。这只是当前选题判断，不是完成全面文献检索后的首创性结论。[AutoChip 后续论文](https://arxiv.org/abs/2411.11856)、[RTLFixer](https://arxiv.org/abs/2311.16543)。

## 六、怎样验证，而不是只讲一个好故事

### 6.1 先区分三种实验问题

| 实验 | 控制方式 | 要回答的问题 |
| --- | --- | --- |
| 生成评价 | 从规格独立生成；固定题集、模型和生成协议 | 系统是否真正改善从规格到 RTL 的端到端结果 |
| 修复评价 | 各组使用完全相同的错误种子、公开规格和评测资产 | 是否改善修复，而不是初始答案恰好更好 |
| 规则迁移评价 | 使用未参与规则提炼、提示修订和调参的新题族，包含合法近邻反例 | 是否迁移应用规则，而不是记住历史题目的修法 |

当前八题已经用于分析和后续设计，只能继续作为开发回归，不能在修订后仍称为未见留出集。改变量名并不足以证明跨题泛化；应变化参数边界、错误组合或结构，同时保证公开规格明确。

### 6.2 分别估计 Host 和 skill 的贡献

最低限度，先让同一冻结 Host 上的 skill ON/OFF 使用相同初始代码、模型、预算及执行规则。若要同时评价 Host 改进，再安排完整的新同期对照：

| 组别 | Host 机制 | Skill |
| --- | --- | --- |
| H0S0 | 冻结的现有 Host | OFF |
| H0S1 | 同一现有 Host | ON |
| H1S0 | 冻结的改进 Host | OFF |
| H1S1 | 同一改进 Host | ON |

H1S0 对 H0S0 用于观察 Host 改进；H1S1 对 H1S0 用于观察新 Host 下的技能收益；四组还能暴露交互效应。全部保留基本安全和权限边界，不通过关闭保护来建立“对照”。不能用已有不同日期、不同协议的实验直接填这张表。

正式裸模型 Baseline 另行保留，不能用 S0 代替。需要先固定最终部署模型组成；若继续保留双模型，应确认相应同模型 Baseline 口径，不能把“仅 8B 裸跑”和“30B 加 8B Agent”的差距全部归因于智能体设计。另做固定总调用或 token 预算的研究对照，区分方法收益与额外计算收益。

### 6.3 建议报告的核心指标

| 指标 | 统计要求 |
| --- | --- |
| 最终有效结果 | 本地四阶段、完整验收、环境阻断分别列示；主分母保留全部预先选定题目 |
| 配对收益与退步 | 同时报告仅 ON 成功、仅 OFF 成功、共同成功、共同失败，不只看总数 |
| 诊断与规则应用 | 依据源码、公开规格及日志复核；记录错误解释、规则误触发及不能判定项 |
| 规划与执行 | 首轮规划合规率、有效补丁比例、关键修改落实情况；格式合格不代替语义正确 |
| 恢复有效性 | 有后续机会的拒绝事件中，有多少形成新动作、EDA 进展和最终通过；三者分别统计 |
| 成本与止损 | 全部成功和失败的调用、token、墙钟及 EDA 次数；同时报告总成本和每成功题成本，防止把提前失败当作提效 |

每轮固定模型版本、上下文、采样配置、预算、评测资产与规则版本；记录实际哪些规则进入了哪些请求。小样本先作开发诊断，不做普遍性结论；扩样前预定统计方法和重复运行安排，保留所有失败，避免反复试验后只选最好一轮。

## 七、下一阶段建议与验收条件

| 阶段 | 主要交付 | 验收条件 |
| --- | --- | --- |
| 第一阶段：清理可避免的流程阻塞 | Probe201 路由正负 fixture；逐字段格式拒绝；逐项无效替换检查；明确代码字段协议 | DUT、TB、环境错误不混淆；边界长度和换行拒绝可定位；历史错误规划不再被误放行；不扩大原预算，不改算旧成绩 |
| 第二阶段：形成最小规则闭环 | 先聚焦枚举、固定接口、过程赋值或握手中的少数高价值规则；附正反例及溯源 | 规则前提可检查，合法反例不误触发，未知形式不伪装为已证明；开发集上能复现检查行为 |
| 第三阶段：冻结新对照 | 固定 Host 下的 ON/OFF；资源允许再做 Host 与 skill 二因素实验；保留新题族 | 能区分工程防护和技能收益；成功与退步均可回放；若无稳定收益，不升级默认技能版本 |
| 第四阶段：正式环境与展示收敛 | 目标版本 EDA、断网环境、AMD/ROCm 单卡运行、合规 Baseline 及演示材料 | 实测模型与 KV cache 等峰值显存、完整流程和资源回收；区分本地诊断结果与正式验收结果 |

目标环境的可行性检查应尽早与前两阶段并行，不必等研究实验结束后才发现部署不可行。若双模型的显存、延迟或复现成本不能满足约束，应优先考虑更简单的单模型加受约束工具方案，再通过对照决定是否保留额外规划模型。

教师 API 仅用于授权范围内的开发与规则整理，不作为正式断网运行依赖。原始失败轨迹、评测版本和旧规则包保持冻结，不能通过补跑、人工修答案或修改评测器回填历史成功。

## 八、比赛答辩怎样展示价值

建议用约 8 至 10 分钟，展示一条完整证据链和一个真实局限，而不是只展示“输入题目，输出代码”的界面。

1. **问题与基线。** 说明硬件修复不只要求能编译，还要保留接口、状态与时序契约；给出真实同期对照及其边界。
2. **成功案例。** 回顾 Probe204：固定标量输入不能被随意扩宽；展示实际局部修改、源码 diff、工具动作和四阶段结果。注明这是错误种子修复，不是从零生成。
3. **失败案例。** 展示 Probe205：方向正确但规划超长，未进入编辑。解释这是协议失败，不能事后算成功；再说明拟如何验证具体反馈是否能改善恢复。
4. **可信性案例。** 用 Probe208 或 Q123 说明“通过仍可能伴随错误诊断或验证盲区”，展示合法反例或独立反证的必要性。
5. **总体证据。** 展示配对成功与退步、成本和未完成项；如下一阶段尚无新结果，明确停留在研究方案，不用动画或模拟输出代替实测。

已有 `rtl-agent.ps1 case` 和历史只读页面适合作为稳定回放入口。新的真实运行应另建目录并单独说明模型与 EDA 前置条件；不能把历史回放说成现场运行，也不能把页面建设当作模型能力创新。现有演示说明见[导师演示指南](deepseek-harness/docs/cookbook/rtl-agent-demo.zh.md)。

## 九、希望与师兄重点讨论的问题

1. **研究主线是否足够集中？** 是否优先研究“失败证据到条件化规则，再到有效恢复”，而不是继续扩展 Agent 数量或功能范围？
2. **最值得切入的失效类别是什么？** 当前枚举约束证据最清楚，握手/FIFO 更能体现硬件语义，但验证成本也更高；应先做哪一类形成完整结果？
3. **什么证据才足以支持创新点？** 除最终通过率外，是否认可把规则误触发、契约违规和无效恢复作为机制性评价，并要求新题族迁移？
4. **技术路线如何取舍？** 双模型是否值得在资源受限场景中保留，还是先用单模型与确定性工具约束建立更清楚的基线，再证明额外规划模型的边际价值？

我的阶段判断是：**项目现在最有价值的资产，是能够还原“为什么失败”的真实轨迹和可重复验证的工程基础。下一步应把这些证据转化为少量有适用边界、能通过新题验证的修复机制，而不是把 skill、图谱或多模型协作本身当作创新结论。** 如果实验最终显示某种技能没有收益，也应保留这一负结果，据此简化方案。
